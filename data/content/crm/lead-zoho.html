Zoho Mail — Entrada de Leads por E-mail

Primeiro esclarecimento, porque quase todo mundo erra: isso não é o Zoho CRM. É o Zoho Mail. O sistema usa a caixa de e-mail da filial no Zoho como canal de captação: os portais (OLX, Webmotors, iCarros, Mobiauto…) mandam o lead por e-mail, o Zoho dispara um webhook de saída para a Boom a cada e-mail recebido, e um parser extrai nome/telefone/e-mail do corpo HTML da mensagem.

Evidência no código (Model/ZohoTable.php):

protected $zohoAuth = "https://accounts.zoho.com/oauth/v2";
protected $zohoApi  = "https://mail.zoho.com/api";

// scopes OAuth
"scope" => "ZohoMail.accounts.ALL,ZohoMail.folders.ALL,ZohoMail.messages.ALL,ZohoMail.attachments.ALL"

É por isso que esse caminho é frágil: a fonte da verdade é um e-mail em HTML, que o portal pode mudar de layout quando quiser, sem avisar.

O webhook

Rota (module.config.php): /webhook/zoho[/:id] → ApiController::zohoAction(), HTTPS.

O :id é a autenticação — não existe token nem assinatura. Ele é o filial_crm_email_id, resolvido por FilialCrmTable::getCrmByIdEmail():

$email_id = preg_replace("/[^0-9]/", "", $email_id);
// ...
->where("f.filial_crm = 1")
->where("fc.filial_crm_email_id = {$email_id}");

O valor é interpolado direto na query — o que segura injeção aqui é o preg_replace que reduz tudo a dígitos, não um prepared statement. Funciona, mas é uma proteção que depende de aquela linha nunca ser removida.

Guards, em ordem

  1. Não é POST ou :id vazio → responde 200 e sai.
  2. Filial não encontrada pelo :id → loga e responde 200. (Há um comentário no código sobre um ID que enche o log: 3EB688188B98F055FE9CA2C8B7BCA37C — "ativo, mas não está no sistema". Note que ele é hexadecimal: o preg_replace vira uma sequência de dígitos que não bate com nada.)
  3. forceAsyncAndContinue() — devolve a resposta e continua processando em background.
  4. $body['sender'] vazio → loga e responde 200.

Todos os caminhos respondem 200, inclusive os de erro. Isso é intencional (evita retry em loop do Zoho), mas significa que lead perdido não gera erro em lugar nenhum visível — só uma linha de log. Quando alguém disser "o lead não entrou", não existe HTTP 4xx/5xx para procurar.

A pegadinha da "Lista de dados limitada"

Na configuração do webhook de saída do Zoho existe a opção:

"Publique apenas a lista de dados limitados, como detalhes de assunto, de, para e hora do e-mail"

Essa opção tem que ficar DESMARCADA. O motivo é direto: marcada, o Zoho manda só metadados (assunto, remetente, destinatário, horário) e não manda o corpo do e-mail. E o corpo é exatamente de onde tudo é extraído:

$bodyWebhook['html'] = trim(preg_replace('/\s+/', ' ',
    (string)(strip_tags((string) $bodyWebhook['html'] ?? ''))));

Sem html, o parser recebe string vazia e não acha nome, telefone nem e-mail do cliente. O lead ou não é criado, ou nasce vazio — e, de novo, o webhook responde 200. Marcar essa caixa é a causa mais comum de "configurei e não entra lead nenhum".

Roteamento: e-mail do remetente decide a origem

Depois de gravar o body, zohoAction() decide o que fazer olhando o fromAddress:

if ($dataFilial['filial_crm_siteproprio'] == $body['fromAddress']) {
    $this->getModel("crm-table")->leadInicial($dataFilial, 20, $body);   // site próprio
} else {
    $origem = $this->getModel("crm-table")->getOrigemRemetente($body['fromAddress']);
    if ($origem) {
        $this->getModel("crm-table")->leadInicial($dataFilial, $origem['crm_origem_id'], $body);
    } else {
        $this->getModel("crm-table")->leadTransacional($dataFilial, $body);  // fallback
    }
}

getOrigemRemetente() consulta sis_crm_origem_remetente com INNER JOIN sis_crm_origem filtrando crm_origem_status = 1. Ou seja: desativar uma origem faz os e-mails dela caírem no fallback transacional, não pararem de chegar.

O parser (CrmTable::leadInicial)

Antes de qualquer coisa, o HTML é reduzido usando duas colunas de sis_crm_origem:

  • crm_origem_tags — allowlist de tags HTML a preservar no strip_tags; o resto vira espaço. Vazio ⇒ default <a>.
  • crm_origem_ponteiro — âncora de texto: strstr() corta tudo antes dela. Serve para pular cabeçalho/assinatura do portal.

Depois vem uma cadeia de elseif com parser dedicado por origem — não existe um formato comum:

Origem sem elseif dedicado cai na extração genérica por crm_origem_remetente_termos, que costuma pegar e-mail mas perder o telefone.

Armadilha de tipo: === com int e string misturados

Os elseif não são consistentes no tipo comparado:

if ($origem === 19 || $origem === "19") {   // defensivo — aceita os dois
} elseif ($origem === "7") {                 // só string
} elseif ($origem === "4" && ...) {          // só string
} elseif ($origem === 20 && ...) {           // só INT
} elseif ($origem === '56') {                // só string
} elseif ($origem === '8') {                 // só string

Isso não é estilo, é comportamento: os dois caminhos que chamam leadInicial() passam o $origem em tipos diferentes — o do site próprio passa o literal 20 (int), e o do remetente passa $origem['crm_origem_id'] vindo do banco. O || $origem === "19" existe justamente porque alguém tropeçou nisso.

Consequência prática: os branches === 20 só disparam pelo caminho do site próprio. Se um dia alguém cadastrar uma linha de origem 20 em sis_crm_origem_remetente, o valor chega como string e todos os parsers de site (AutoConf, Hostinger, MotorSync, RevendaMais) param de rodar em silêncio — o lead é criado, só que sem telefone e sem título. Hoje não há nenhuma linha com origem 20 nessa tabela, então o problema está latente, não ativo.

leadTransacional() — o fallback

Remetente que não bate com nenhuma origem ativa não é descartado: vai para leadTransacional(). É o balde onde cai e-mail de portal novo ainda não cadastrado, resposta de cliente e mensagem automática de sistema. Ao investigar "portal X não vira lead", o primeiro lugar a olhar é se o remetente dele está em sis_crm_origem_remetente.

Como debugar um lead que não entrou

Todo webhook — inclusive os que falham — grava o payload cru antes de qualquer processamento:

$dataWebhook = [
    "filial_crm_id" => $dataFilial['filial_crm_id'],
    "filial_crm_webhook_body" => json_encode($bodyWebhook),
    "url" => $_SERVER['REQUEST_URI']
];
$this->getModel("crmwebhook-table")->save($dataWebhook);

Roteiro:

  1. Chegou? Procure em sis_crm_webhook pelo filial_crm_id e janela de horário. Não achou ⇒ o problema é no Zoho (webhook desligado, :id errado), não na Boom.
  2. Chegou com corpo? Se html vier vazio no JSON, é a "Lista de dados limitada" marcada.
  3. Roteou certo? Confira o fromAddress do payload contra sis_crm_origem_remetente (e se a origem está com crm_origem_status = 1).
  4. Parseou? Se o lead nasceu sem telefone, o layout do e-mail do portal provavelmente mudou — o parser daquela origem precisa de ajuste.

Os logs de exceção do zohoAction saem com módulo webhook_zoho; os de log estruturado, com pasta webhook / arquivo zohoAction. Em produção eles estão no Papa Entulho (logs_legacy_exceptions / logs_legacy_exceptions_custom), não no New Relic — ver New Relic.

O caminho que substitui isso

Já existe uma rota moderna que evita o parser inteiro: ApiController::leadAction(), um POST estruturado direto do site do cliente, autenticado com o mesmo site-token (Bearer, kid por site) que o site já usa para estoque. O docblock é explícito:

"Cria um lead a partir de um POST estruturado do SITE do cliente — substitui o caminho e-mail → Zoho → zohoAction → leadInicial (parser). […] Payload estruturado (telefone incluso) elimina o bug do fone perdido."

Aceita dry_run para o Centralizador testar elegibilidade sem criar nada, exige nome + (email ou telefone), e usa cod_filial só se pertencer ao master (senão cai na primeira filial com CRM, para não perder o lead). Para site próprio, prefira essa rota ao fluxo de e-mail.

Envio de resposta (Zoho Mail API)

ZohoTable::sendMessage() responde o lead pela mesma caixa, com action: reply quando há messageId. O access token é renovado por refreshToken(), que persiste o novo token e o expires via FilialCrmTable::updateZohoToken(). Esse fluxo tem log próprio (pasta zoho-refresh-token, com lastOnly = false e expiração de 7 dias) — é o primeiro lugar a olhar quando uma filial para de conseguir responder e-mail.
