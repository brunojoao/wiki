Credere / MultiBanco — Simulador e Propostas de Financiamento

Documentação técnica do módulo MultiBanco (integração com a Credere — meucredere.com.br), responsável por simulações e propostas de financiamento de veículos no app.boomsistemas.com.br.

⚠️ Atenção, dev novo: ao contrário do integrador legado de portais, este módulo é moderno e bem estruturado: usa Guzzle V7, propriedades tipadas (PHP 7.4), helper Cache (sessão), OAuth2 com refresh automático e webhooks. A nomenclatura externa é "MultiBanco"; o provedor por trás é a Credere.

3. URLs e cliente HTTP

Definidas em config/constants.php:

define('CREDERE_API_BASE_URL', 'https://app.meucredere.com.br/api/v1/');
define('CREDERE_EMBED_BASE_URL', 'https://embed.meucredere.com.br/');

O cliente HTTP é um Guzzle V7 (GuzzleHttpV7\Client) criado em createHttpClient() (~linha 2083) com base_uri => CREDERE_API_BASE_URL e um HandlerStack com middlewares. Atribuído a $this->httpClient no construtor.

O embed (iframe) aponta para:

  • CREDERE_EMBED_BASE_URL . "simulations/form" → criar/preencher simulação
  • CREDERE_EMBED_BASE_URL . "simulations/read" → ler simulação existente

 

4. Configuração por filial (onde se configura)

Tudo é configurado por filial, na tabela sis_filial_multibanco_config, pela tela do MultiBancoFilialConfigController. A flag sis_filial.filial_fl_multibanco liga/desliga o módulo.

Actions de config (MultiBancoFilialConfigController): salvarAction(), deletarAction(), testarTokensAction(), renovarTokensAction(), resumoDadosAction(), dadosCompletosJsonAction(), registrarBackupAction(), excluirDadosAction() (delete cascata, só com backup recente).

 

5. Autenticação OAuth2 (dois tokens + refresh automático)

O módulo opera com dois tokens distintos por filial: embed (limitado) e proposals (completo). A escolha é feita em getTokenForEndpoint() (~2102):

  • Chamadas de API (endpoint ≠ get-embed-url) sempre usam o proposals token.
  • Para gerar a URL do embed: usuário master recebe o proposals token; demais dependem da permissão view_bank_return (com permissão → proposals; sem → embed token).

Carregamento e validação (em setup(), ~83):

setup()
  ├─ checkPermission(userId, filiais)                 // autoriza acesso ao módulo
  ├─ Cache "multibanco_loja_config" (TTL_LONG, sessão)
  │     └─ filialConfigByFilialId() → tokens, store_id, plano
  ├─ isTokenValid(token_expires_at)                   // DateTime vs now (America/Sao_Paulo)
  └─ popula $credereAccessToken, $credereProposalsAccessToken, $credereStoreId, $planoCliente

Toda chamada à API passa por requestJson($method, $endpoint, $options) (~2131), que injeta os headers padrão:

Authorization: Bearer {token apropriado}   // via getTokenForEndpoint()
Store-Id: {credereStoreId}
Accept: application/json

Refresh automático: se a resposta for 401 ou 403, o requestJson():

  1. descobre se o token usado era proposals ou embed;
  2. pega o refresh token correspondente do config;
  3. chama performTokenRefresh($refreshToken, $tokenType, $filialId) (~156) → POST token com grant_type=refresh_token (usa o Guzzle direto, não o requestJson, para evitar loop);
  4. persiste os novos tokens (MultiBancoFilialConfigTable::updateTokens()) + atualiza cache de sessão;
  5. repete a requisição original. Há trava $refreshAttempted[$tipo_filial] para não tentar refresh duas vezes no mesmo request.

 

6. Fluxo: criar uma simulação

1. /multi-banco/nova-simulacao  (novaSimulacaoAction)
      └─ usuário escolhe veículo (searchVehicles/getVehicleDetails) + cliente (searchCustomers/getClientDetails)
2. Backend monta a URL do embed (getTokenForEndpoint('get-embed-url'))
      └─ iframe: CREDERE_EMBED_BASE_URL + "simulations/form"
3. Usuário completa a simulação dentro do iframe da Credere
4. Front faz POST → criarSimulacaoApiAction com o simulation.uuid
      └─ INSERT em:
           sis_simulacoes_financiamento          (registro principal)
           sis_veiculo_simulacao_financiamento    (snapshot do veículo)
           sis_lead_simulacao_financiamento       (snapshot do lead/cliente)
5. enrichSimulationWithApiData() / fetchSimulation(uuid)  // puxa dados completos da API
6. Retorna JSON → front redireciona para /multi-banco/visualizar/{id}

Sincronização manual: sincronizarSimulacoesAction() percorre simulações pendentes (simulationNeedsApiUpdate()), chama fetchSimulation() e grava via updateSimulationWithApiData(), recalculando o approval_status.

 

7. Webhooks (sincronização vinda da Credere)

8. CredereHelper — regras de negócio

Centraliza a lógica que não depende de I/O:

  • Constantes de evento + isValid() / getPayloadKey() (mapeia evento → chave do payload JSON).
  • mapCredereStatusToInternal() — converte o status da Credere para o status interno, com metadata (priority, is_final, is_success).
  • analyseSimulation() — true se há banco com pre_approval_status >= 2 e available = true (define se a simulação tem chances).
  • bestBanks() — retorna até 5 bancos com melhores condições (menor juros / parcela).
  • isSuccessStatus(), isFinalStatus(), normalizeStatusInput() (remove acentos), getAllStatusByPriority().

Status interno (do menor ao maior): checagem → em_analise → pendente → pre_aprovada → aprovada → faturada; e os finais negativos recusada, recusada_restricao, desistencia.

  • Master: grupo_acesso_id != 3 — acesso total (sempre recebe o proposals token).

  • Permissões ficam em sis_multibanco_user_permissions e são cacheadas em sessão (multibanco_user_{user_id}_*).

12. Pontos de atenção para um novo dev

  • Nunca chame a API montando token na mão — use requestJson(); ele resolve token, headers e refresh.
  • Dois tokens: lembre que API = proposals token; embed pode usar embed token conforme permissão. Bugs de "401" quase sempre são token errado para o endpoint.
  • Config é por filial: ao testar, garanta que a filial tem sis_filial_multibanco_config preenchido, tokens válidos e filial_fl_multibanco = 1.
  • Webhooks são a fonte de verdade do status: a simulação/proposta evolui via credereAction(). Para reprocessar, consulte sis_credere_webhook.
  • Soft delete: simulações usam deleted_at — filtre por deleted_at IS NULL nas queries.
  • Exclusão em massa (excluirDadosAction) exige backup recente — não burlar.
  • Status: para qualquer regra de "aprovado/recusado/final", use CredereHelper, não compare strings na mão (há acentos e mapeamento).
  • Cache de sessão: config e permissões ficam em cache (multibanco_loja_config, multibanco_user_permission). Em mudanças de token/permissão, o cache precisa expirar/ser invalidado.
