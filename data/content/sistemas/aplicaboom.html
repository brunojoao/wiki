AplicaBoom — Aplicativo Flutter

Aplicativo mobile em Flutter/Dart (Android e iOS), no repositório Projects/aplicaboom. Ele consome exclusivamente a AplicaBoom API — não fala com app.boomsistemas.com.br, boomia nem api.boomsistemas.com.br diretamente. Se o app precisar de dado de outro serviço da stack, quem faz a ponte é a API dele.

Esta página é o que você precisa saber para trabalhar no app: os comandos, onde ele aponta em cada ambiente, como a arquitetura é organizada e as armadilhas que já custaram tempo do time. A API tem página própria; a infraestrutura de produção está em Arquitetura de Infraestrutura.

1.1 Depurar contra produção

O run-prod sobe em --release: sem hot reload, sem DevTools e com stack trace ofuscado pelo R8. Para depurar de verdade contra a API de produção, é o mesmo env/prod.json sem o --release:

flutter run --dart-define-from-file=env/prod.json -t lib/main_prod.dart

São dados reais. Criar lead, mover card e ação em lote gravam no CRM de produção. O selo PROD no cabeçalho do menu e na tela de login é a única pista visual — em produção o endereço da API é omitido de propósito.

Existe um alvo make run-prod-debug com essa receita (e um DEVICE= opcional, porque com Linux, Chrome e celular ligados o flutter run para para perguntar qual usar). Ele entrou em 14/09/2026: se não estiver no seu clone, use a linha acima.

1.2 O SDK certo, e o snap que atrapalha

O projeto foi criado com Flutter 3.47.2 / Dart 3.13.2, instalado em ~/development/flutter. Existe um snap do Flutter 3.19 em /snap/bin que não atende o projeto (o pubspec exige Dart ^3.13.2).

O ~/.bashrc põe o SDK certo na frente do PATH, mas shell não-interativo não lê esse bloco — então qualquer comando disparado por ferramenta (bash -c, script de CI, agente) pega o snap e falha com erro de versão de SDK. Nesses contextos, prefixe sempre:

export PATH="$HOME/development/flutter/bin:$PATH"

1.3 Onde rodar: desktop, emulador ou celular

Os plugins camera, firebase_core, firebase_messaging, permission_handler e video_player não têm implementação Linux: no desktop eles lançam MissingPluginException em runtime. É a lista do que obriga a sair do desktop.

No emulador, -gpu host não é detalhe: com o renderizador por software o emulador consome 214% de CPU, contra 10% usando a GPU.

emulator -avd Pixel_3a_API_34_extension_level_7_x86_64 \
  -gpu host -memory 2048 -cores 2 -no-boot-anim -no-snapshot-save

Celular físico que não aparece no adb devices: lista vazia é diferente de unauthorized. unauthorized significa que falta aceitar a chave RSA na tela; lista vazia significa que o aparelho não está expondo ADB nenhum — confira se a depuração USB está mesmo ligada (lsusb -v deve mostrar uma interface classe 255, subclasse 66, além da de MTP). Em aparelho que não coopera por USB, a depuração sem fio do Android 11+ resolve: parear com código, e depois adb connect na porta que o adb mdns services informar — ela é diferente da porta de pareamento.

2. Ambientes e o endereço da API

O endereço não vem de .env lido em runtime: vem de String.fromEnvironment, assado no bundle pelo --dart-define-from-file. É de propósito — o que é compilado no bundle é legível por qualquer pessoa que abra o APK.

ArquivoAPI_BASE_URLEntrypointEstado
env/dev.jsonhttp://10.0.2.2:3334main_dev.dartemulador
env/dev_desktop.jsonhttp://127.0.0.1:3334main_dev.dartdesktop
env/prod.jsonhttps://api.boomsistemas.com.br/aplicaboommain_prod.dartno ar
env/staging.jsonhttps://staging.aplicaboom-api.boomsistemas.com.brmain_staging.dartnão existe

Trocar de ambiente exige recompilar. Não há como apontar o app instalado para outro servidor.

A API vive num CAMINHO do gateway, não num subdomínio. Não existe aplicaboom-api.boomsistemas.com.br — a ideia foi descartada em set/2026 (exigiria certificado ACM, SNI no listener do kong-elb e registro no Route 53 para um host que só o app consome). E só HTTPS: http://api.boomsistemas.com.br/aplicaboom não responde, porque nenhum dos dois balanceadores tem listener na porta 80.

O prefixo faz parte da base, e as rotas de ApiEndpoints começam com /. O Dio concatena os dois (.../aplicaboom + /v1/auth/login); rota sem a barra inicial grudaria no prefixo e viraria .../aplicaboomv1/.... Uma "limpeza" que tirasse as barras quebraria produção inteira, e nenhum outro teste perceberia — todos usam base sem caminho. Há teste prendendo isso em test/core/network/api_base_url_test.dart.

2.1 O selo de ambiente

AmbienteBadge (shared/widgets/ambiente_badge.dart) é uma pilha com bolinha e o nome curto do flavor, no cabeçalho do menu lateral e na tela de login.

Ele aparece em TODOS os flavors, produção inclusive. Um selo que some em produção não distingue "é produção" de "esqueceram de colocar o selo" — e depois de instalados os builds são idênticos por fora: mesmo ícone, mesmo nome, mesmo applicationId. O endereço da API acompanha o selo só fora de produção, onde a pergunta costuma ser "estou batendo no emulador ou na máquina?".

O banner DEBUG do Material não resolve isso: ele diz se o build é de depuração, não para qual servidor aponta — um release do flavor dev não mostra banner nenhum.

2.2 Versão exigida pela API

Antes de qualquer tela, inclusive do login, o app consulta GET /v1/app/versao (pública, sem banco e sem Redis) e compara versao_app_requerida com a própria versão do pubspec.yaml. Divergiu, ele bloqueia a tela pedindo atualização. null significa "não exijo versão".

$ curl -s https://api.boomsistemas.com.br/aplicaboom/v1/app/versao
{"versao_app_requerida":"1.0.0","versao_api":"2026.09.03.0"}

Só preencha APP_VERSION_REQUIRED em produção com uma versão já publicada na loja: ninguém consegue atualizar para uma versão que não existe, e o efeito seria trancar a base inteira do lado de fora.

3. Arquitetura

Clean Architecture organizada por feature, com Riverpod fazendo injeção de dependência e estado. As dependências apontam para dentro: presentation → domain ← data, e todas as três podem usar core.

CamadaPode importarNão conhece
domain/nada do projetoDio, SharedPreferences, Flutter
data/domain, corepresentation
presentation/domain, coredata — fala por caso de uso
core/corefeatures, nunca

core nunca importa features é a regra mais fácil de quebrar sem perceber; quando isso acontece, core vira refém de uma feature e o projeto perde a possibilidade de testar em partes. O SessionManager ilustra: ele mora em core/session e não em features/auth, porque o interceptor HTTP (que é core) precisa dele.

3.1 A trilha do erro

Uma trilha só, do socket até a tela:

DioException
   ▼ ErrorInterceptor
AppException          (NetworkException, ServerException, ...)
   ▼ mapExceptionToFailure, na fronteira do repositório
Failure               (NetworkFailure, AuthFailure, ...)
   ▼ AsyncValue.guard
AsyncError            capturado pelo Riverpod
   ▼
ErrorView             switch exaustivo sobre o Failure

Duas decisões explicam o formato: repositórios lançam Failure, não devolvem Result (o AsyncValue já carrega o erro até a UI; empilhar um Result por cima seria escrever duas vezes o mesmo tratamento), e Failure é sealed — criar um tipo novo de falha quebra a compilação até alguém decidir como ele aparece para o usuário.

3.2 Estado e navegação

  • Todos os providers usam geração de código (@riverpod). @Riverpod(keepAlive: true) para serviços e repositórios; @riverpod (autoDispose) para controllers de tela — é o que garante que a câmera libere o hardware ao sair da tela.
  • Providers expõem tipos abstratos (AuthRepository, nunca AuthRepositoryImpl), o que permite trocar a implementação inteira num teste com overrideWithValue.
  • Nenhuma tela navega depois de autenticar. A tela de login só muda o estado; quem decide o destino é o redirect do go_router. Duas fontes de navegação competindo é a causa clássica de tela piscando e pilha corrompida.
  • O router é criado uma vez; mudanças de sessão chegam por refreshListenable. Recriar o router a cada login apagaria o histórico.

3.3 Refresh de token concorrente

O AuthInterceptor anexa o Bearer e, no 401, renova a sessão e repete a requisição. O detalhe que importa: várias requisições podem receber 401 ao mesmo tempo. A renovação fica guardada num Future compartilhado — a primeira falha dispara o refresh, as demais aguardam o mesmo resultado. Sem isso, N requisições paralelas disparariam N refreshes e o backend invalidaria o token.

E o cliente que faz o refresh (DioFactory.createPlainClient) não tem o AuthInterceptor: se tivesse, um 401 no próprio refresh dispararia outro refresh, em recursão.

4. Design System

Tokens extraídos do Figma App Boom. lib/core/theme/ tem AppColors (nomes espelham as variáveis do Figma), AppTypography (Inter nos títulos, Mulish no corpo), AppSpacing/AppRadius/AppSizes e AppSemanticColors — extensão de tema para sucesso/aviso/informação, que o ColorScheme do Material não cobre.

lib/shared/design_system/ guarda os componentes que espelham o Figma e não conhecem Failure nem Riverpod; lib/shared/widgets/ fica com os widgets de aplicação (ErrorView, AsyncValueView). Catálogo visual em /dev/design-system, registrado só no flavor dev, alcançável pelo botão no rodapé do login.

O ColorScheme é montado campo a campo, não por ColorScheme.fromSeed — o algoritmo tonal do Material 3 devolveria primos das cores do Figma, não elas.

Pendências conhecidas: raios de borda não confirmados no Figma; a cor de aviso não existe no layout (o âmbar atual está marcado como não-oficial); e branco sobre o ciano #009FE3 dá 2,9:1, abaixo do WCAG AA.

5. Autenticação

O app usa uma senha própria, separada da senha do sistema web. O motivo: o app.boomsistemas.com.br autentica contra sis_user com MD5 sem salt (Module.php:734, DbTableAuthAdapter com 'MD5(?)'), e as 13.196 senhas do banco têm exatamente 32 caracteres. Levar esse esquema para dentro de um aplicativo distribuído transformaria um problema conhecido num problema maior.

A credencial mora em sis_user_app_auth (hash scrypt); sis_user continua sendo a referência de identidade e de acesso — user_id, grupo_acesso_id e filial_id saem de lá. O contrato das rotas e os códigos de recusa estão na página da API.

Do lado do app, o que importa: o corpo do erro traz um code estável, e o app decide por ele sem comparar texto. 401 é credencial (reabre o formulário); 403 é "quem você é não pode entrar agora" (mostra o motivo e não insiste).

5.1 O erro de login fica na tela

Não é snackbar. Era, com 4 segundos de duração, e a queixa que chegava era "não entra e não diz por quê": numa falha de rede a espera pode chegar aos 20s do connectTimeout, e quem tocasse em Entrar e olhasse para o lado voltava a um formulário sem explicação.

A faixa sai do próprio authState, sem cópia no State: some sozinha quando a tentativa seguinte começa (isLoading) ou dá certo (AsyncData).

As três abas vazias estão registradas de propósito: aba que não navega para nada parece defeito, e a barra do layout tem as cinco.

As abas vivem numa StatefulShellRoute.indexedStack, cada uma com pilha própria — trocar de aba e voltar preserva a rolagem do quadro e não refaz as requisições.

6.1 Decisões de tela que valem saber

  • Um controller por grupo de dados, não por card. Cinco widgets do painel saem da mesma varredura; cada bloco carrega com seu próprio esqueleto, falha com seu próprio InlineErrorView e refaz só a si mesmo.
  • O quadro é um carrossel de uma coluna por página (viewportFraction: 0.92, para a coluna seguinte espiar na borda). A paginação é por coluna: a pessoa pode estar na terceira página de "Novo lead" e na primeira de "Negociação".
  • Sem arrastar e soltar. No celular o gesto horizontal é do carrossel; arrastar o card competiria com ele. Mover é por ação explícita.
  • O # do card é o crm_lead_ticket, não o id. O badge de tempo é o tempo desde a última interação, não tempo na etapa — o legado calcula assim, e tempo na etapa exigiria histórico de status, que não existe no banco.
  • O quadro se atualiza sozinho por três gatilhos: laço de 20s com a aba na frente, volta do segundo plano e puxar para atualizar. O laço pergunta GET kanban/versao e compara com a resposta anterior — a primeira conferida nunca recarrega, senão o quadro se recarregaria sozinho ao abrir.
  • Ação em lote recarrega o quadro inteiro, diferente das ações de um card, que corrigem o card na hora: a seleção atravessa colunas e o servidor devolve uma contagem, não os cards.
  • O botão "Responsável" só aparece para gerente, via permissoes.alterar_responsavel que o servidor manda junto com as colunas. O app não recalcula a regra — quem decide é quem escreve.

7. Armadilhas que já custaram tempo

Esta seção é a razão de a página existir. Todas são reais e todas têm teste ou precedente.

7.1 Centenas de erros no analyze = codegen velho

Erro de Undefined name 'state', Undefined name 'ref' ou provider inexistente não é código quebrado: é um *.g.dart que não foi gerado. Um arquivo faltando derruba em cascata todo mundo que usa o provider dele.

make gen        # resolve
make clean && make gen   # se sobrou .g.dart conflitante depois de renomear classe

Confirmação rápida: o part '<arquivo>.g.dart'; existe no fonte e o .g.dart não existe na pasta.

7.2 AsyncValue.when, nunca switch sobre AsyncData/AsyncError

O Riverpod 3 tenta de novo sozinho quando a requisição falha, e nesse meio-tempo o estado é AsyncLoading com erro dentro. Um case AsyncError não casa com isso e a coluna ficaria com o esqueleto na tela para sempre. when olha hasError.

7.3 Todo botão dentro de uma Row precisa de minimumSize próprio

O tema define minimumSize: Size.fromHeight(...) para os três tipos de botão (app_theme.dart:159+), e Size.fromHeight é largura infinita — botão de formulário, que ocupa a linha toda. Numa Row isso estoura em BoxConstraints forces an infinite width e o widget inteiro não renderiza.

Foi exatamente o que manteve a barra de seleção do quadro invisível desde que ela foi escrita: nenhum teste marcava um card, então ninguém viu.

7.4 Providers autoDispose em teste

Controller de folha e de filtro é autoDispose. Em teste que monte a folha sozinha, sem a tela, é preciso um container.listen para o estado sobreviver ao aplicar — senão o provider é descartado no instante seguinte à escrita e o valor se perde.

O contrário também morde: CrmKanbanRevalidacao é keepAlive, e isso é o ponto todo. A tela chama conferir() por ref.read, sem observar o resultado; com autoDispose o provider morreria a cada chamada, a referência voltaria a null toda vez e o laço nunca acharia diferença — sem quebrar nada, só não funcionando.

7.5 pumpAndSettle trava com esqueleto na tela

A animação do SkeletonBox/SkeletonLine é em laço, então pumpAndSettle nunca retorna. Use pump(Duration).

7.6 Abrir uma folha em teste precisa de dois pump

O primeiro só empilha a rota; a animação de entrada começa no frame seguinte, e com um pump só a folha ainda está fora da tela — o toque cai no vazio e a falha não diz por quê.

7.7 O rótulo obrigatório carrega o asterisco

CustomTextField e CustomDropdownField desenham o rótulo com Text.rich, e find.text compara o texto plano do span — então é find.text('Status *'), não 'Status'. E não dá para tocar no rótulo para abrir um seletor: ele fica FORA da caixa e dentro de um ExcludeSemantics; o caminho é o Semantics que embrulha o campo, que carrega o rótulo sem o asterisco.

7.8 A data viaja como hora de parede

2026-09-13T14:30, sem fuso e sem segundos. Nada de toIso8601String(): o servidor grava a string crua, e UTC deslocaria o lead três horas em relação ao mesmo lead criado pelo sistema web.

7.9 Rolagem com o mouse no desktop

AppScrollBehavior acrescenta PointerDeviceKind.mouse aos dragDevices. O padrão do Flutter só aceita arrasto de dispositivos "tipo toque", então no Linux/Windows/macOS o carrossel e as listas parecem travados: segurar o botão e arrastar não rola nada. Em celular não muda nada.

7.10 compileSdk só quebra no build nativo

O app compila contra a API 37 (acima do flutter.compileSdkVersion), porque permission_handler e flutter_secure_storage exigem — sem isso o build falha no checkDebugAarMetadata. E o compileSdkMinor = 0 é a parte que costuma faltar: o SDK Manager publica esse nível como android-37.0, e sem o minor o AGP procura android-37, não encontra e falha com Failed to find target with hash string 'android-37'.

Ao atualizar dependências, rode flutter build apk --debug antes de abrir o PR: erro de compileSdk nunca aparece no flutter analyze nem nos testes.

8. R8: o que quebra só no release

flutter_secure_storage 11 guarda os tokens com Tink (com.google.crypto.tink:tink-android) e não traz regras de ProGuard próprias — conferido no pub-cache, não há nenhum .pro no android/ dele.

O problema não é o R8 remover, é o R8 renomear: o Tink registra os gerenciadores de chave por nome e desserializa protobuf por reflexão, então com os nomes trocados ele estoura na primeira leitura. Como o R8 só roda no release, o sintoma era o aplicativo travar na splash e terminar em "Não foi possível ler os dados salvos no aparelho" — com tudo funcionando em desenvolvimento.

As regras estão em android/app/proguard-rules.pro. Para conferir se um plugin sobreviveu com o nome:

~/Android/Sdk/cmdline-tools/latest/bin/apkanalyzer dex packages \
  build/app/outputs/flutter-apk/app-release.apk | grep -ci tink

Zero significa renomeado (ou ausente). Antes das regras: tink 0, nomads 0; depois: tink 33774, nomads 490.

Todo plugin novo que use reflexão (Gson, protobuf, Tink, serialização por nome de classe) precisa de regra aqui — e o release é o único lugar onde a falta dela aparece.

9. Publicar

Android

O release só assina de verdade com android/key.properties no lugar (modelo em key.properties.example); sem ele o Gradle cai na chave de debug, para que flutter run --release funcione em máquina sem o keystore.

Um APK assim a Play Store recusa — era o estado anterior, conferido com apksigner: CN=Android Debug. O .jks e o key.properties estão no .gitignore, e perder o keystore significa não conseguir mais publicar atualização.

iOS

Exige macOS com Xcode. Falta preencher o DEVELOPMENT_TEAM (hoje CODE_SIGN_STYLE = Automatic com iPhone Developer) e registrar o App ID; o bundle id já é br.com.boomsistemas.aplicaboom, igual ao Android. No primeiro build num Mac: cd ios && pod install (é este comando que gera o Podfile, por isso ele não está no repositório), as macros do permission_handler no Podfile — sem elas o plugin compila com todas as permissões ligadas e a Apple rejeita o app —, as capabilities de push no Xcode e aps-environment como production no build de distribuição.

10. Convenções

  • Arquivos em snake_case, classes em PascalCase, um conceito por arquivo.
  • class para tudo que os testes precisam mockar (datasources, repositórios, serviços) — final class impede implements fora da biblioteca e o mocktail deixa de funcionar. final class para hierarquias fechadas (Failure, AppException); abstract interface class para contratos.
  • Cor e fonte saem do Theme, nunca escritas na tela. Espaçamento vem de AppSpacing, não de número solto.
  • Rota não se escreve à mão — use AppRoute.
  • BuildContext depois de await exige if (!context.mounted) return; — o analisador trata como erro, não aviso.
  • Nunca inferir nome de coluna do banco legado: rode DESCRIBE antes. O acesso ao banco é somente leitura.
  • Commits convencionais, em português: feat(crm): quadro se atualiza sozinho.

Para criar uma feature nova, features/auth/ é a referência — ela tem o caminho completo das nove etapas (entidade → contrato → casos de uso → model → datasource → implementação → providers → controller → rota), com make gen e os testes no fim.

11. Pendências conhecidas

  • Firebase/push desligado. O app roda sem Firebase — as notificações locais funcionam e o push fica desligado, com aviso no log. Para habilitar, docs/NOTIFICACOES.md.
  • Staging não existe. O env/staging.json aponta para um host inexistente; quando houver staging, provavelmente seguirá o mesmo padrão de caminho no Kong.
  • Contraste do ciano abaixo do WCAG AA (2,9:1), e a cor de aviso ainda não-oficial.
  • Distribuição automática de lead (o rodízio que a loja usa para repartir os leads que chegam sozinhos) continua só no legado. A criação manual nunca passou por ele, nem lá.
  • Quem recebe lead por atribuição em lote feita pelo app não é avisado — a API não tem push nem socket, e pela web o legado dispara notificação. Pendência da API, não do app.
