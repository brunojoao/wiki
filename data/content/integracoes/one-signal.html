Autenticação por header Authorization: Basic {REST_API_KEY} (padrão da REST API v1 do OneSignal — a chave vai crua, não é base64 de user:pass).

A REST API key é read + write. Um único POST /notifications com included_segments: ["All"] dispara push para a base inteira (hoje ~82 mil devices registrados). Para auditoria, use só GET. No PC de dev há um guard-rail de PreToolUse (~/.claude/hooks/prod-write-guard.py) que bloqueia método de escrita para onesignal.com antes de executar.

A chave que liga usuário Boom ↔ dispositivo

Esta é a parte que mais confunde:

public static function buildUserId($uid)
{
    return $uid . '_' . sha1("__" . $uid);
}

O external_user_id registrado no OneSignal não é o user_id puro — é <user_id>_<sha1("__" . user_id)>. O prefixo com o id em claro serve para inspeção; o sufixo sha1 funciona como uma assinatura fraca, para que não se consiga notificar um usuário arbitrário só chutando um número sequencial.

Implicação prática: ao procurar um usuário no painel do OneSignal, busque pelo valor completo. E qualquer código que envie push tem que passar por buildUserId() — mandar o user_id cru resulta em notificação que não chega e nenhum erro (o OneSignal aceita o request e simplesmente não acha destinatário).

Para montar o id de um usuário na mão:

php -r 'echo $argv[1]."_".sha1("__".$argv[1]);' 12964

Pegadinhas do send()

1. Kill switch que muda o tipo de retorno

if (Desabilitador::isDisabled('one-signal-push') || IS_NOT_PRODUCTION) {
    return 'desabilitado';
}

Duas coisas aqui:

  • Push nunca sai fora de produção. Não adianta testar notificação em dev/staging — o método sai antes do cURL. Para testar de verdade, é no ambiente de produção, pela rota de teste do Admin Dashboard.
  • O retorno vira string. No caminho normal a função devolve ['success' => bool, 'response' => ..., 'http_code' => int]; desabilitada, devolve a string 'desabilitado'. Qualquer chamador que faça $send['success'] sem checar o tipo lê 'd' (offset de string) ou dispara warning. Ao consumir o retorno, teste is_array($send) primeiro.

O Desabilitador::isDisabled('one-signal-push') é a chave para desligar push em produção sem deploy — útil em incidente de spam de notificação.

2. Espaçamento entre envios (era sleep(1))

Atualizado (ago/2026). O sleep(1) incondicional que existia depois de cada curl_exec foi removido. Custava ~17.000 s de worker por dia só no webhook de WhatsApp (45% do tempo dele), inclusive quando o request mandava um único push — caso em que não havia nada para espaçar. E como o sleep era por worker, nunca funcionou como rate limit global: com 90 workers saíam 90 pushes/s do mesmo jeito.

O que existe hoje:

const INTERVALO_MINIMO = 1.0;       // segundos entre dois envios do MESMO worker
private static $ultimoEnvio = 0.0;

if (self::$ultimoEnvio > 0.0) {
    $desde = microtime(true) - self::$ultimoEnvio;
    if ($desde < self::INTERVALO_MINIMO) {
        usleep((int) round((self::INTERVALO_MINIMO - $desde) * 1000000));
    }
}

Quem manda um push só não paga nada; uma sequência de pushes no mesmo worker continua espaçada como antes. Também entraram timeouts de cURL (CURLOPT_CONNECTTIMEOUT e CURLOPT_TIMEOUT = TIMEOUT_MEDIUM) — antes não havia teto nenhum. É MEDIUM e não SMALL de propósito: sendToMultipleUsers() manda um lote de ids, e um teto curto derrubaria o lote inteiro, que aqui vira notificação perdida sem retry.

A recomendação de preferir sendToMultipleUsers() a um loop de sendToUser() continua valendo — uma chamada em vez de N.

3. CURLOPT_SSL_VERIFYPEER = false

curl_setopt($ch, CURLOPT_SSL_VERIFYPEER, false);

A validação do certificado TLS está desligada na chamada para o OneSignal. Como a REST API key vai no header dessa mesma requisição, isso enfraquece a proteção contra interceptação no caminho. Não há motivo técnico aparente (o certificado do onesignal.com é público e válido) — é candidato a remoção.

4. Falha de push não está sendo logada

if (!$out['success']) {
    handleLog(false, json_encode($out), 'one-signal', 'push', false, '2026-03-31 23:59:59');
}

O último parâmetro é o $expires do handleLog(), e a implementação descarta o log quando a data já passou:

if ($expiryDate && $now > $expiryDate) {
    return;   // sai sem gravar nada
}

Como 2026-03-31 já passou, todo erro de push é silenciosamente descartado desde então. HTTP 400/401/429 do OneSignal não aparece em lugar nenhum. Se a suspeita for "push parou de chegar", esse log não vai ajudar até alguém empurrar a data (ou remover o parâmetro). Isso não é exclusivo do OneSignal — ver a seção de logs expirados em New Relic.

Lado do dispositivo — por que o usuário não recebe

Todo o resto desta página trata de envio. A maioria absoluta dos cartões de suporte sobre notificação, porém, não é envio: é assinatura. O usuário nunca virou um destinatário válido. Esta seção é o roteiro para provar isso em minutos, sem depender de print.

Como o cliente assina

Dois caminhos, ambos só aparecem em produção e com usuário logado:

  • Sininho flutuante do OneSignal (notifyButton.enable: true no init). É ele que mostra o modal "Unblock Notifications" quando a permissão está bloqueada.
  • Sininho do header (#notification-one-signal em menu.phtml), que chama OneSignal.Notifications.requestPermission() / PushSubscription.optIn().

Pegadinha: em layout.phtml há uma lista de URLs onde o sininho flutuante é escondido por CSS:

$urlsOcultas = ['lead', 'crm/view/list'];
// -> display:none em div#onesignal-bell-launcher

O strpos é sobre a REQUEST_URI inteira, então qualquer URL que contenha a substring lead esconde o sininho flutuante. Se o cliente vive na tela de leads e diz "não tem onde ativar", é isso — o sininho do header continua lá, mas o flutuante não.

A regra dura: permissão negada é beco sem saída para o código

Quando Notification.permission === 'denied', a spec da Notifications API manda o navegador resolver requestPermission() na hora, sem exibir prompt. Não existe SDK, versão ou truque que reabra aquela janela — nem o OneSignal, nem código nosso. A liberação é obrigatoriamente manual, nas configurações do navegador do usuário.

É por isso que o modal "Unblock Notifications" do OneSignal só mostra instruções: é tudo o que ele pode fazer. Antes de abrir investigação de bug, confirme se não é este caso — economiza horas.

Melhoria pendente no nosso lado: hoje, com a permissão em denied, clicar no sininho do header não faz nada — sem prompt, sem aviso, sem erro (menu.phtml:182-207). O SDK v16 expõe OneSignal.Notifications.permissionNative ('default' | 'granted' | 'denied'), então dá para detectar e mostrar o passo a passo em vez do silêncio.

Como o usuário libera, por dispositivo

Samsung Internet (Android)

  1. ☰ → Configurações → Sites e downloads → Notificações → localizar boomsistemas.com.br → Permitir.
  2. Se o site não aparecer na lista: Configurações → Privacidade e segurança → Dados pessoais do navegador → limpar dados do site e acessar de novo (o prompt volta ao estado inicial).
  3. Checar o Samsung Push Service: Configurações do Android → Apps → menu → Mostrar apps do sistema → Samsung Push Service → tem que estar ativado. Desativado, o Samsung Internet não emite token mesmo com tudo permitido.

Chrome (Android)

  1. ⋮ → Configurações → Configurações do site → Notificações → boomsistemas.com.br → Permitir.
  2. Android 13+ tem duas camadas. Além da permissão do site, o app Chrome precisa de permissão de notificação no SO (POST_NOTIFICATIONS): Configurações do Android → Apps → Chrome → Notificações → ativado. Liberar só uma das duas não resolve, e é o erro mais comum na triagem — o print do suporte quase sempre mostra a camada do SO, não a do site.
  3. Web push no Chrome Android depende do Google Play Services. Aparelho sem GMS (ou com GMS desativado) não recebe.

Chrome / Edge (desktop)

  • chrome://settings/content/notifications (ou edge://settings/content/notifications) → procurar o site → Permitir.
  • Para zerar de vez: chrome://settings/content/siteDetails?site=https://boomsistemas.com.br → Redefinir permissões.
  • No Windows, checar Assistente de foco / Não perturbe e Configurações → Sistema → Notificações para o navegador. A notificação pode estar chegando e sendo suprimida pelo SO.

iOS / iPadOS (Safari)

  • Web push exige iOS 16.4+ e, obrigatoriamente, o site adicionado à Tela de Início (Compartilhar → Adicionar à Tela de Início). No Safari em aba comum não funciona, por decisão da Apple. Depois de instalar, abrir pelo ícone e ativar o sininho.
  • Confirmado funcionando: há SafariPush com token válido na frota.

Bateria e segundo plano (Samsung/Xiaomi principalmente)

  • Configurações → Bateria → Limites de uso em segundo plano → o navegador não pode estar em "apps em suspensão" nem em "apps em suspensão profunda".
  • Configurações → Apps → navegador → Bateria → Sem restrições.
  • Isso não impede a assinatura, mas atrasa ou engole a entrega. Sintoma típico: chega tudo de uma vez quando o usuário abre o navegador.

Bloqueador de anúncios e DNS filtrante

Causa subestimada e fácil de confirmar. O domínio onesignal.com está em listas de privacidade largamente usadas (EasyPrivacy, ativada por padrão no uBlock Origin), então:

  • Desktop: extensão de bloqueio (uBlock, AdBlock, AdGuard, escudos do Brave) impede o OneSignalSDK.page.js de carregar. O sininho simplesmente não aparece e nenhuma subscription é criada.
  • Android: DNS privado apontando para AdGuard/NextDNS bloqueia em todos os navegadores do aparelho de uma vez.

Assinatura de reconhecimento: no OneSignal não existe registro nenhum daquele navegador — nem -99. Se o usuário jura que tentou e não há registro, é isso.

Teste que o suporte pode pedir, sem termo técnico: abrir este endereço direto no navegador —

https://cdn.onesignal.com/sdks/web/v16/OneSignalSDK.page.js

Se aparecer código, está liberado. Se der erro ou página em branco, está bloqueado. Correção: liberar boomsistemas.com.br no bloqueador, ou Configurações → Conexões → Mais configurações de conexão → DNS privado → Desativado.

Checklist de diagnóstico

Primeiro descubra de que lado está o problema. Uma consulta ao endpoint de usuário separa "não assinou" de "não enviamos", e é sempre o passo 1.

Lado do dispositivo (assinatura)

  1. Existe subscription daquele aparelho? GET /apps/{app_id}/users/by/external_id/{buildUserId}. Não existe ⇒ o SDK não rodou ali (bloqueador, DNS filtrante, ou nunca logou nesse navegador).
  2. O token está vazio? Vazio ⇒ não existe destinatário, e nenhum envio vai chegar nunca.
  3. notification_types = -10? Permissão negada no site. Só o usuário reverte — mandar o procedimento do navegador dele.
  4. -99 com 0-1 sessão? Registro fantasma, ignorar. Ele nunca respondeu ao prompt.
  5. Android 13+: conferir as duas camadas (permissão do site e permissão de notificação do app navegador no SO).
  6. iOS: o site está adicionado à Tela de Início? Sem isso não existe web push.
  7. O sininho aparece? Em URL que contenha lead ou crm/view/list, o flutuante é escondido por CSS — usar o do header.

Lado do servidor (envio)

  1. Está em produção? Fora dela, send() devolve 'desabilitado' e nada sai.
  2. O kill switch está ligado? Conferir as três flags em Desabilitador.php.
  3. O id está no formato certo? Tem que ser buildUserId($user_id), não o user_id cru. Id errado = HTTP 200 e ninguém notificado.
  4. Erro de API? Hoje não há log (pegadinha 4). Para investigar, empurre a data do handleLog ou inspecione o retorno no ponto de chamada.
  5. Origem confere? O SDK tem que rodar em boomsistemas.com.br, mesma origem do chrome_web_origin do app.
