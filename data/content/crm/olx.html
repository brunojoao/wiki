OLX — Leads e Chat

Lead de OLX entra no CRM por dois caminhos independentes, e a diferença entre eles é a causa do problema mais reclamado da integração: o lead aparece, mas a aba de chat não.

Cerca de dois terços dos leads de OLX não têm chat. Nos últimos 90 dias são 22.007 leads, dos quais só 7.430 têm olx_chat_id. A tendência é de melhora lenta (27% → 35%), mas isso é o normal da integração, não uma anomalia pontual.

Query para reconferir:

SELECT DATE_FORMAT(crm_lead_data,'%Y-%m') AS mes,
       COUNT(*) AS leads,
       SUM(olx_chat_id IS NOT NULL) AS com_chat,
       ROUND(100*SUM(olx_chat_id IS NOT NULL)/COUNT(*),1) AS pct
FROM sis_crm_lead
WHERE origem_id = 2 AND crm_lead_data >= '2026-03-01'
GROUP BY mes ORDER BY mes;

Caminho 1 — webhook nativo (com chat)

Rota: /chat-olx-65613f41-c104-450e-bf19-f19c03e340b4/:filial_id — o UUID no path é anti-scan (o comentário no module.config.php diz isso literalmente), não autenticação. Handler: CrmOlxTable::receiveMessage().

O que ele faz, em ordem:

  1. Carrega as colunas do funil (sis_crm_status) da filial e monta a lista de status visíveis (crm_status_view). Sem colunas ⇒ aborta com log [OLX] Erro ao buscar status do lead.
  2. Procura lead existente por olx_chat_id = chatId dentro dos status visíveis. O chatId é a chave da conversa, não o telefone nem o e-mail.
  3. Se não existe e $origin === 'seller', ignora — é mensagem da loja, não do comprador, e não deve abrir lead.
  4. Se não existe e é do comprador, cria o lead.

O lead criado por esse caminho é o único que nasce completo para chat:

"origem_lead"      => 2,
"titulo_lead"      => "Contato via OLX (chat)",
"cliente_lead"     => $data['name'] ?? "Lead OLX Sem Nome",
"telefone_lead"    => telefoneMask($senderPhone),
"email_lead"       => $senderEmail,
"chat_external_id" => "55" . $senderPhone,
"olx_chat_id"      => $chatId,        // <-- o que habilita o chat
"olx_anuncio_id"   => $listId,
"meta_recipient_id"=> null,           // Não é Meta
"meta_sender_id"   => null,           // Não é Meta
"ia_atendimento"   => $iaConfig['canal_ativo'] ? 1 : 0,

Note o "55" . $senderPhone hardcoded em chat_external_id: assume Brasil. Telefone estrangeiro fica com DDI errado.

Caminho 2 — e-mail via Zoho (sem chat)

Quando o contato vem como proposta por e-mail (noreply@olx.com.br), ele entra pelo pipeline genérico de e-mail: zohoAction() → getOrigemRemetente() → leadInicial($filial, 2, $body). Detalhes em Zoho - Leads.

leadInicial() monta o $dataLead a partir do HTML do e-mail e nunca inclui a chave olx_chat_id. E CrmTable::saveLead() só grava a coluna se a chave existir no array:

if (isset($lead['olx_chat_id'])) {
    $data['olx_chat_id'] = $lead['olx_chat_id'];
}
if (isset($lead['olx_anuncio_id'])) {
    $data['olx_anuncio_id'] = $lead['olx_anuncio_id'];
}

Resultado: coluna fica NULL. Não é bug de gravação — é ausência de dado na origem. O e-mail da OLX simplesmente não carrega o identificador da conversa; ele não existe naquele payload. Por isso não adianta "corrigir o parser": sem chatId, não há conversa para responder.

Por que a aba de chat some — o erro exato

O envio de mensagem (CrmIntegracaoController, ~linha 847) exige o chatId do lead:

$chatId = $lead['olx_chat_id'] ?? null;
if (empty($chatId)) {
    return $this->getResponse()->setContent(json_encode([
        "error" => true,
        "msg"   => "Chat ID da OLX (chatId) não encontrado no lead para envio."
    ]));
}

Antes disso ainda há o guard de configuração:

if (!$olxConfig || empty($olxConfig[0]['token'])) {
    throw new \Exception("Configuração OLX não encontrada ou Token de acesso está vazio para a filial.");
}

São duas causas diferentes para "não consigo mandar mensagem", e as mensagens distinguem: "Chat ID da OLX (chatId) não encontrado" = lead veio por e-mail; "Token de acesso está vazio" = integração da filial não conectada (/olx-crm → olxCrmConnect).

O merge Zoho + chat

Quando os dois caminhos disparam para o mesmo contato (o comprador manda e-mail e abre chat), o webhook tenta reaproveitar o lead que o Zoho já criou, em vez de duplicar:

$paramsToFind = [
    'status_id'      => $colunasIn,
    'filial_id'      => $filialId,
    'crm_lead_email' => trim($senderEmail),
    'origem_id'      => 2
];
sleep(1);
$findForZoho = $globalTable->getMagic('sis_crm_lead', ['crm_lead_id'], $paramsToFind);

if (!empty($findForZoho)) {
    $alreadyExistsByZoho = true;
    $dataLead['id_lead'] = $findForZoho[0]["crm_lead_id"];
    handleLog(true, 'chat_already_exists_zoho => ...', 'olx', 'chat_already_exists_zoho', ...);
}

Com id_lead preenchido, saveLead() entra no ramo de UPDATE ($this->update($data, 'crm_lead_id = ' . $lead['id_lead'])) em vez de INSERT — então o lead do Zoho recebe o olx_chat_id de volta e o chat passa a funcionar. É por isso que alguns leads de e-mail ganham chat depois.

Dois pontos frágeis aqui, ambos reais:

  • sleep(1) — é uma espera cega para dar tempo de o webhook do Zoho terminar de gravar. Se o Zoho demorar mais que 1s, o merge não acontece e nasce um lead duplicado. Se for mais rápido, é 1 segundo de worker parado em toda mensagem de chat de lead novo.
  • A chave do merge é o e-mail. Se a OLX não mandar email no payload do chat ($data['email'] ?? null), crm_lead_email vai vazio, o getMagic não casa e o merge falha — duplicando.

Quando o merge acontece ($alreadyExistsByZoho === true), a atribuição de responsável é pulada de propósito (if ($filialCrmTipo > 0 && $alreadyExistsByZoho === false)) — o lead já tem dono do fluxo do Zoho, não faz sentido redistribuir.

Como auditar

Os dois desfechos do merge geram log na mesma pasta/arquivo, mudando só o status:

pasta: olx | arquivo: chat_already_exists_zoho
[OK]   = achou o lead do Zoho e fez merge
[FAIL] = não achou, criou lead novo

Em produção esses logs estão no Papa Entulho (logs_legacy_exceptions_custom), com expires_at em 2026-04-30 nas chamadas atuais — vale conferir se ainda estão dentro da validade antes de contar com eles.

Envio de mensagem para a OLX

POST https://apps.olx.com.br/autoservice/v1/chat/send
Authorization: Bearer {olxToken}

{
  "textMessage": "...",
  "messageId":   uniqid('olx_', true),
  "chatId":      "{olx_chat_id do lead}"
}

Só texto — não há upload de anexo nesse caminho (diferente do Meta, que tem etapa de attachment_id). O messageId é gerado localmente com uniqid(); o comentário no código observa que a OLX exige o campo mas gerencia o ID final.

Resumo para o suporte

  • Lead OLX sem aba de chat é o comportamento esperado quando ele veio por e-mail — hoje, ~2 em cada 3. Não é falha de configuração da filial.
  • Lead OLX com chat tem olx_chat_id e olx_anuncio_id preenchidos. Para confirmar: consultar essas colunas em sis_crm_lead.
  • "Token de acesso vazio" é outro problema: filial não conectada na OLX.
  • Origem 55 olx-chat existe em sis_crm_origem, mas o código não a usa — o webhook grava origem_lead = 2. Não filtre por 55 esperando achar os leads de chat.
