New Relic

Existem dois agentes New Relic diferentes rodando em produção, e eles não têm nada a ver um com o outro além do nome. Confundir os dois é a causa de quase toda dúvida sobre "o New Relic não está pegando o servidor X".

  • Agente de Infraestrutura (newrelic-infra) — roda no host, via systemd. Coleta CPU, memória, disco, rede e métricas dos containers Docker. Não sabe nada de PHP.
  • Agente APM PHP — roda dentro do container php7, é uma extensão do PHP. Coleta transações, erros, queries e traces. É ele que define as entidades BoomSistemas-Master e BoomSistemas-Slave-1 no APM.

Cada um é ativado num lugar diferente: o de infra pelo systemctl no host, o de PHP pelo docker-compose.yml do serviço php7. Ligar um não liga o outro.

Ativando os agentes

Agente de infraestrutura (host)

sudo systemctl enable newrelic-infra
sudo systemctl status newrelic-infra

Config em /etc/newrelic-infra.yml (contém a license_key). O enable é o que garante que ele volte depois de um reboot — importante no slave, que é desligado e religado todo dia (ver abaixo).

Agente APM PHP (container)

Configurado no docker-compose.yml do serviço php7. O parâmetro que importa é o appname: é ele que decide em qual entidade do APM os dados caem. Se os dois hosts subirem com o mesmo appname, os dados dos dois se misturam numa entidade só e fica impossível separar master de slave num incidente.

Como as transações são nomeadas — e o problema de cardinalidade

Em app.boomsistemas.com.br/public/index.php:41, antes de o Zend bootar:

if (extension_loaded('newrelic')) {
    // Usa a URI da requisição para dar nome à transação no painel
    newrelic_name_transaction($_SERVER['REQUEST_URI']);
}
Zend\Mvc\Application::init(require 'config/application.config.php')->run();

Por isso todas as transações aparecem como WebTransaction/Custom/<uri>. O guard extension_loaded('newrelic') é o que faz o mesmo código rodar em dev sem a extensão instalada.

O efeito colateral: REQUEST_URI inclui path params e query string. Isso gera um nome de transação novo para cada variação de URL. Medido em 24h:

  • 21.868 nomes únicos de transação no BoomSistemas-Master (20.833 no slave)
  • 129.204 transações/dia com ? no nome — ex.: crm/getleads?view=quadro, login?q=%252Fcrm%252Fnotificacoes, api/fullestoque?veiculo_id=0, api/home/filial/577?

O New Relic recomenda ficar na casa do milhar de nomes únicos; acima disso ele aplica metric grouping issue e passa a colapsar segmentos em * por conta própria. É exatamente o que já acontece com o webhook do PlugMessage, que aparece agrupado como:

WebTransaction/Custom/webhook/plugmessage/*/status
WebTransaction/Custom/webhook/plugmessage/*/receber

Ou seja: o agrupamento está sendo feito pelo New Relic, não pela aplicação — e onde ele não colapsa, a lista de transações vira ruído. Para consertar de verdade, a URI deveria ser normalizada antes de virar nome: cortar a query string e substituir IDs numéricos por placeholder.

DRIVER_LOG_MODE — o switch que decide se o New Relic recebe log

Todo tratamento de erro e log do sistema legado passa por config/deep_debug.php, que tem três drivers selecionados por uma variável de ambiente:

// DRIVER_MODE: 0 = arquivo, 1 = New Relic, 2 = PapaEntulhoDb
function _getDriverMode(): int
{
    return (int) getenv('DRIVER_LOG_MODE');
}

Detalhe importante do modo 1: quando é o New Relic quem recebe, handleException() enriquece o erro com contexto de sessão — dados que não existem nos outros dois drivers:

newrelic_notice_error($e->getMessage(), $e);
newrelic_add_custom_parameter('module', $module);
if ($complement) newrelic_add_custom_parameter('complement', $complement);
if (isset($session->usuario->user_id)) {
    newrelic_add_custom_parameter('user_id', $session->usuario->user_id);
    newrelic_add_custom_parameter('user_full_name', ...);
}

E handleLog() fatia a mensagem porque o New Relic corta atributo em ~4096 bytes — cada log vira N eventos AppLogs costurados por um log_id compartilhado (part / total), em pedaços de 250 caracteres.

Qual modo está em produção hoje

Modo 2 (Papa Entulho), não New Relic. Evidência direta:

SELECT count(*) FROM AppLogs SINCE 30 days ago
-- 0

Nenhum evento AppLogs nos últimos 30 dias. Ou seja: todo o caminho de log estruturado para o New Relic é código morto em produção hoje — os 361 handleLog() gravam no MariaDB do Papa Entulho (logs_legacy_exceptions_custom), não no APM. Isso bate com o .env.example, que documenta DRIVER_LOG_MODE=2 # use 2 somente para production.

Consequência prática: ao caçar um erro, os erros que aparecem no APM (aba Errors) chegam lá pela instrumentação automática do agente PHP, não pelo handleException(). Erro tratado dentro de um try/catch que chama handleException() está no Papa Entulho e não no New Relic. Procure nos dois.

Vale notar o fallback: se o PapaEntulhoDb não conseguir conectar (timeout de 2s), ele chama handleLog(..., forceFile: true) e o log vai para arquivo no container — nunca para o New Relic. Perda silenciosa de log se ninguém olhar o disco.

Logs que expiraram e ninguém percebeu

O 6º parâmetro de handleLog() é $expires, e a implementação descarta o log quando a data já passou:

if ($expires !== null) {
    $now = new DateTime();
    // ... converte timestamp | string | DateTime
    if ($expiryDate && $now > $expiryDate) {
        return;   // sai sem gravar em lugar nenhum
    }
}

A ideia é boa: log de investigação temporária se apaga sozinho, sem virar lixo permanente. O problema é que a data é escrita à mão na chamada, e ninguém volta para revisar.

Varredura no app.boomsistemas.com.br: existem 25 chamadas de handleLog() com data fixa, e todas as 25 datas já passaram (a mais recente é 2026-08-23). Ou seja, nenhuma delas grava nada hoje.

Retenção: o APM só guarda 8 dias

Medido na conta 7544045: consulta em Transaction retorna dados a partir de 18/08/2026 e zero antes disso (janela de 26/08). Confirmado com:

SELECT count(*) FROM Transaction TIMESERIES 1 day SINCE 12 days ago UNTIL 6 days ago

Não adianta abrir o APM procurando um incidente de três semanas atrás — não existe mais. Para histórico longo, a fonte é o Papa Entulho (que persiste em tabela) ou os gráficos de métricas agregadas, não os eventos brutos.

Pegadinha: o slave desliga às 20h (não é incidente)

O boomsistemas-legado-slave é ligado e desligado por duas Lambdas em sa-east-1:

  • LigarSlaves — sobe a instância ~08h
  • DesligarSlaves — derruba a instância ~20h

Observado em 26/08/2026: a instância subiu às 08:00 BRT e o último dado no New Relic foi exatamente 20:00 BRT, com StateTransitionReason: "User initiated (2026-08-26 23:05:19 GMT)". No fim de semana ela nem sobe — no gráfico de 7 dias, o BoomSistemas-Slave-1 tem dois dias inteiros zerados.

Portanto: buraco no gráfico do slave à noite ou no fim de semana é comportamento esperado, não queda. Já buraco no BoomSistemas-Master é anomalia real — o master roda 24/7 (ligado desde 30/09/2025, sem restart).

Consequência para o agente de infra: como o slave reinicia todo dia, systemctl enable newrelic-infra nele não é opcional. Sem o enable, o agente sobe uma vez na mão e some no próximo ciclo.

Resumo dos pontos abertos

  • Cardinalidade de transação — 21.868 nomes únicos/dia. Normalizar a URI em public/index.php antes do newrelic_name_transaction() (cortar query string, trocar ID numérico por placeholder).
  • Log estruturado desligado — o caminho AppLogs nunca é exercitado em produção (DRIVER_LOG_MODE=2). Ou se assume que a fonte de log é o Papa Entulho, ou se liga o modo 1; hoje o código dos dois existe e só um roda.
  • Sem alerta configurado — as duas entidades APM estão com alertSeverity: NOT_CONFIGURED. Nada dispara sozinho, o New Relic hoje só serve para consulta manual.
