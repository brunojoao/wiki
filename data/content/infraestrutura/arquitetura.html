Arquitetura de Infraestrutura

Mapa da infraestrutura da Boom levantado via AWS CLI read-only (profile claude-ro), Admin API do Kong de produção e inspeção SSH das EC2. Coleta: 27/08/2026.

Conta AWS 384916510164. Região de produção: sa-east-1 — 1 VPC, 10 EC2, 4 RDS, 2 ALB, 2 Lambda. Existe ainda 1 VPC + 1 EC2 solta em us-west-1 (Elastic Beanstalk do homolog); as outras 15 regiões estão vazias.

1. Visão geral: DNS, rede e entrada

1.1 A topologia real da VPC

Antes do diagrama, três fatos que contrariam o desenho "de manual" e explicam quase todas as decisões de security group abaixo:

  • A VPC é a default da conta — vpc-0fc84ab2372e975e1, 172.31.0.0/16, criada pela AWS, não por IaC.
  • Não existe subnet privada. As três subnets têm MapPublicIpOnLaunch = true e compartilham uma única route table (rtb-0ec61782c27a3c22c, a main) com rota 0.0.0.0/0 → igw-0d131388d2fa1b434. Toda EC2 nasce com IP público.
  • Não existe NAT Gateway. Não há o que rotear: nada está atrás de subnet privada.

Consequência prática: o isolamento da infra é 100% security group. Não há camada de rede por baixo dele. Se um SG abrir, o recurso está na internet.

2.1 Quem acessa a porta 3306

Duas portas de entrada distintas no mesmo banco, e é importante não confundi-las:

  1. Por security group — sg-0a6f0b9803553870e aceita 3306 do SG ec2-rds-4. É por aqui que as cinco EC2 de aplicação falam com o banco. Tráfego interno da VPC, sem passar pela internet.
  2. Por IP público — sg-044518faf56a13082 (rds) aceita 3306 de sete /32 públicos: 189.4.122.30, 189.4.123.12, 189.4.104.145, 45.166.204.43, 187.56.78.67, 162.120.186.148, 138.122.67.42. São as máquinas do time — é o que faz o DBGate local conectar em produção.

Sobre o "isolamento" do RDS

Vale registrar sem rodeio, porque a suposição comum é a oposta: as quatro instâncias RDS estão com PubliclyAccessible = true e resolvem para IP público. Não há proibição de acesso externo em nível de rede — o que impede o mundo de conectar é exclusivamente a lista de sete IPs do SG rds.

Isso funciona, mas tem três consequências operacionais que valem estar documentadas:

  • IP residencial do time muda. Quando um dev "perde o acesso ao banco do nada", a causa quase sempre é essa lista — não credencial.
  • A superfície do banco é a internet inteira, filtrada por SG. Sem criptografia em repouso (StorageEncrypted = false) e sem rds.force_ssl no parameter group custom, a conexão do DBGate trafega em claro se o cliente não pedir TLS.
  • Retenção de 2 dias no master é curta para recuperar erro humano descoberto na segunda-feira sobre algo feito na sexta.

Nada disso é incidente e nada precisa mudar hoje — mas é a diferença entre o desenho presumido e o desenho real, e é a informação que falta quando alguém for planejar a próxima mudança de banco.

O slave roda a mesma stack e é ligado/desligado por Lambda (seção 6). Fora da janela, SSH nele dá timeout — é esperado, não é incidente.

KONG_TRUSTED_IPS=0.0.0.0/0 combinado com REAL_IP_HEADER=X-Forwarded-For é o que faz o Kong enxergar o IP real do cliente em vez do IP do ALB — necessário para o rate-limiting contar por consumidor certo. O efeito colateral é que o Kong confia no X-Forwarded-For de qualquer origem; como a 8400 só aceita tráfego do SG do ALB, na prática só o ALB consegue injetar esse header.

Duas exposições que merecem revisão

  • Grafana na 3000 aberto para 0.0.0.0/0 (launch-wizard-2). A proteção é só o login do Grafana. Restringir aos mesmos IPs da 8401/8402 seria coerente com o resto.
  • Admin API na 8401 exposta na interface pública, restrita a 4 IPs. A Admin API do Kong OSS não tem autenticação — RBAC é recurso Enterprise. Quem alcança a 8401 tem controle total do gateway: criar rota, remover plugin de auth, ler credencial de consumer. O SG é a única trava, e ela é por IP.

Como o app chega no Gotenberg

A porta 3000 nunca é publicada. Quem autentica é o nginx, no bloco location /gotenberg/:

    auth_basic_user_file /etc/nginx/htpasswd;
    proxy_pass http://boom-gotenberg:3000/;
    client_max_body_size 32m;

    proxy_send_timeout   120s;

O app configura DOCUMENTOS_PDF_CHROMIUM_URL=https://usuario:senha@boom-centralizador.duckdns.org/gotenberg. Verificado na coleta: /gotenberg/ devolve 401 com TLS válido.

Três detalhes que quebram se alterados sem atenção:

  • O nome no proxy_pass é boom-gotenberg, não gotenberg — são projetos Compose diferentes, e só o container_name atravessa entre eles.
  • A barra final do proxy_pass corta o prefixo, por isso a URL do app termina em /gotenberg sem barra.
  • Os limites de 32 MB e 120s são contrato, não folga. O corpo leva HTML mais imagens em data URI, e o render passa de 1s no cold start (~3s medido). Os defaults do nginx — 1 MB de corpo e 60s de leitura — cortariam os dois casos.

A armadilha do fastcgi_pass

O bloco location ~ \.php$ do nginx está comentado desde 05/08/2026, e o comentário explica por quê: com o container php8 fora do compose, o fastcgi_pass php8:8001 fazia o nginx falhar ao subir com "host not found in upstream". Isso derrubaria o proxy do Gotenberg no próximo restart. Se o Centralizador um dia vier para esta máquina, é preciso descomentar o bloco E devolver o serviço php8 ao compose — na ordem certa.

4. Kong API Gateway

Kong 3.9.1 OSS, backend Postgres, rodando na EC2 kong. Configuração extraída da Admin API de produção (:8401) na data da coleta.

4.1 Upstreams e targets — não existem

Resposta direta, porque é a primeira coisa que se procura: o Kong de produção tem zero upstreams e zero targets.

GET /upstreams  → {"data": []}
GET /targets    → nenhum
GET /certificates → {"data": []}
GET /snis       → {"data": []}

Os services apontam direto para host e porta, sem camada de balanceamento do Kong. Isso significa que:

  • Não há load balancing nem health check ativo de upstream. Se o api-main cair, o Kong continua encaminhando para ele e devolvendo erro — não existe alvo alternativo para onde desviar. A resiliência hoje é o retries: 5 de cada service, nada além disso.
  • O service api-loja aponta para o IP público do api-main (52.67.152.88). É um Elastic IP, então sobrevive a stop/start e pode ser reassociado a uma instância nova — o endereço não é volátil. O incômodo real é outro: o tráfego Kong→API sai pelo IGW e volta, em vez de usar o IP privado 172.31.15.71.
  • TLS não termina no Kong. Sem certificado e sem SNI cadastrados: o ALB kong-elb termina o HTTPS com certificado ACM e fala HTTP puro na 8400.

Migrar os services para upstream com dois targets é o caminho natural quando houver uma segunda instância da API — e é pré-requisito para qualquer deploy sem downtime.

Notas de comportamento:

  • accept_http_if_already_terminated: true no oauth2 é obrigatório aqui. O TLS termina no ALB e o Kong recebe HTTP puro; sem essa flag o plugin recusaria o fluxo OAuth por não estar em HTTPS.
  • policy: local no rate-limiting. O contador vive na memória do nó Kong. Com uma instância isso é exato — quando houver a segunda, o limite efetivo passa a ser o dobro do configurado, porque cada nó conta o seu. A migração é apontar o plugin para Redis.
  • O rate limit do boomia é permissivo por desenho (15/s com teto de hora praticamente aberto): tráfego interno do CRM, não parceiro externo.
  • O bot-detection está cadastrado mas desabilitado. Não protege nada hoje; está lá como esqueleto.
  • Sem request-transformer, sem http-log e sem file-log. Não há transformação de header nem log de acesso via plugin — o log do Kong é o do container, coletado pelo Promtail para o Loki.

4.5 Consumers e o modelo de autorização

ConsumerPapel
systemsIntegrações internas
adminsAcesso administrativo
carchat-usersIntegração CarChat — ver CarChat
cnpj-restrict-request-usersParceiros com escopo travado por CNPJ

A autorização acontece em três camadas empilhadas sobre o mesmo service api-loja:

  1. oauth2 autentica e resolve qual consumer está chamando.
  2. acl autoriza por área. Como o plugin está no service e as rotas de área têm regex própria, o efeito é que /v1/loja/{id}/financeiro/* e /v1/loja/{id}/crm/config exigem que o consumer pertença ao grupo correspondente.
  3. post-function restringe por identidade. Para o consumer cnpj-restrict-request-users, um script Lua compara o CNPJ presente no path com o nome da credencial usada — impede que um parceiro autenticado leia dados de outra loja apenas trocando o ID na URL. É a única regra de tenant isolation que roda no gateway; os demais consumers não passam por ela.

O provision_key do plugin oauth2 é segredo do gateway e não está reproduzido nesta página — consultar direto na Admin API quando necessário.

Como este mapa foi levantado

Para refazer a coleta quando a infra mudar:

  • AWS: export AWS_PROFILE=claude-ro e os describe-*/list-* de ec2, rds, elbv2, route53, lambda, s3, cloudfront. O profile é somente leitura por IAM e por hook local.
  • Kong: GET em /services, /routes, /plugins, /upstreams, /consumers, /certificates, /snis na Admin API — só funciona a partir de um dos 4 IPs liberados no launch-wizard-2.
  • EC2: SSH com a key new-prod-sp (hosts no config do Terminator) e docker ps + leitura do docker-compose.yml de cada stack.

Valores de senha, token e provision_key foram deliberadamente omitidos desta página.
