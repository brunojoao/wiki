Módulo de Contratos — Arquitetura Técnica

Como funciona, tecnicamente, o módulo de Contratos/Documentos do app.boomsistemas.com.br (Zend Framework 2 / PHP 7.x): anatomia de um contrato, os dois motores de geração, placeholders, mPDF, tabelas, fluxos de customização e as principais pegadinhas. Leitura obrigatória antes de criar/alterar qualquer contrato.

 

1. Anatomia de um contrato

Cada contrato/documento é a soma de:

1 registro em sis_contrato      (metadados: descrição, template, view, fonte, margem, flags)
 + 1 template HTML              public/template/<nome>.html  (~475 templates hoje)
 + (opcional) 1 view .phtml     module/Application/view/application/contratos/<nome>.phtml
 + <option> nos dropdowns        veiculo/edit.phtml, contratos/novo.phtml, contratos/clausula.phtml

O template é HTML com placeholders %Nome% que o backend substitui pelos dados (cliente, veículo, filial, valores...). O mPDF transforma o HTML final em PDF.

 

2. Princípio mestre — software de prateleira

O BoomSistemas é software de prateleira. Clientes pedem personalizações o tempo todo; o trabalho é resolver no menor nível possível. Hierarquia (do preferido ao mais restrito):

  1. Template (public/template/*.html) — onde a personalização deve ficar sempre que possível.
  2. View custom (*.phtml) — quando precisa de campos diferentes ou automação de frontend (JS). É o limite "tranquilo".
  3. Backend (ContratosTable.php, controller) — evite. Já há muito if (filial_id == ...) legado; a meta é restringir.

Regra de ouro do backend: só altere a lógica se beneficiar todos os clientes. Adições genéricas (um placeholder novo lendo um campo do veículo, um fix amplo) podem ser feitas sem confirmar. Código específico de filial (if (filial_id == X)) deve ser evitado e sempre confirmado antes. Prefira a via neutra: placeholder gated por flag/campo postado em vez de filial_id.

Outro princípio: prefira placeholders dinâmicos a texto fixo — mesmo quando o cliente manda o modelo já preenchido (aquele exemplo é só uma geração; o template serve a todas as filiais). Exceção: quando não existe chave que resolva o dado, ou o usuário orienta que é fixo.

 

3. Arquitetura — hierarquia usuário master → filiais

O sistema não tem o nível grupo/empresa → filiais. Cada filial é subordinada a um "usuário master" (cliente) via user_id. Relação canônica: user_id (master) → filial_id (várias filiais por master).

  • O que personaliza conteúdo (cláusulas, contrato personalizado) costuma chavear por user_id.
  • O que é acesso/edição nas telas usa filial_id ($this->usuario->filial_id_real).
  • Procuradores (sis_filial_procurador) chaveiam por filial_id, NÃO por master.

⚠️ Nunca assuma — verifique a coluna real (user_id vs filial_id) da tabela-alvo antes de filtrar.

Motor de PDF: use Mpdf; no ContratosController.

 

5. Tabelas

sis_contrato — o registro/metadados do contrato:

⚠️ Os campos contrato_fonte/contrato_size/contrato_margin são do registro base, compartilhado por todas as filiais.

sis_contrato_configuracao — override de fonte/tamanho/margem por filial (não há UI; INSERT manual em produção): contrato_config_id, filial_id, contrato_id, contrato_config_size, contrato_config_fonte (aceita decimal), contrato_config_margin (ou NULL → cai na base). Usado em getContratoConfig() nas 3 actions de PDF e na assinatura digital. O override só vale se contrato_config_fonte != "".

sis_clausula_contrato — cláusula personalizada por master: clausula_contrato_id (PK), contrato_id, user_id, clausula_contrato (text).

sis_contrato_personalizado (legado — só produção) e sis_filial_procurador (procuradores) — ver seções 11 e 10.

 

6. ⚠️ Duas telas, DOIS motores de geração

Este é o conceito mais importante. O mesmo contrato pode ser gerado por dois caminhos diferentes, com fontes de dados distintas:

Consequência: não invente placeholders custom (%CNH_Cliente%, %Opcionais%...) para um contrato gerado na página do veículo — saem literais. Use só chaves que geraDataContrato produz. Se precisar do dado nos dois fluxos, adicione a chave em geraDataContrato (de forma genérica).

⚠️ Se um contrato existe nas duas telas, gere o PDF pelos dois fluxos e dê diff (os motores divergem em silêncio). Atenção a lookup de pessoa, %Valor%, datas e %Clausula%. Um placeholder não-resolvido sai literal no PDF.

Passo final comum aos dois: saveContrato() — faz mb_strtoupper em todos os valores postados (~linha 278) e roda os str_ireplace dos placeholders, o swap PJ e os motores de bloco.

 

7. Placeholders — chaves de geraDataContrato (página do veículo)

Conjunto fixo disponível no motor da página do veículo:

  • Comprador/venda: Cliente, CPF_Cliente, RG_Cliente, CPFCNPJ_Cliente, Email_Cliente, Tel_Cliente, Cel_Cliente, Nacionalidade_Cliente, Profissao_Cliente, EstadoCivil_Cliente, Nascimento_Cliente, Endereco_Cliente, Endereco_Num_Cliente, Bairro_Cliente, UF_Cliente, CEP_Cliente, Endereco_Complemento, DtVenda, HrVenda, Valor, Vendedor
  • Veículo: Marca, Veiculo, Modelo, Ano, AnoFab, AnoMod, Placa, Chassi, Motor, Km, Cor, Renavam, Combustivel, Potencia, Origem, DtEntrada, AntigoProprietario, CPF_AntigoProprietario
  • Filial: Filial, Filial_Endereco, Filial_Num_Endereco, Filial_Bairro, CEP_Filial, Filial_Telefone, CNPJ_Filial, UF_Filial, Filial_Logo, Procurador, ...
  • Data/especiais: dd, mm (nome do mês), yyyy, hh, %Logo%, %Clausula%, %Observacoes%.

As chaves do cliente/outorgante são inicializadas como string vazia no array inicial → na ausência de dados saem em branco (não literais). Ao criar placeholders de cliente novos, dê default vazio aqui também.

 

8. ⚠️ mPDF — limitações de CSS

  • Não suporta writing-mode nem transform: rotate. Para texto vertical use a propriedade própria text-rotate: 90; inline.
  • colgroup/table-layout:fixed não são confiáveis para células vazias (colapsam). Ponha width explícito em cada <td> (com &nbsp; nas vazias).
  • Especificidade: .classe td { border:none } vence .box { border }. Use seletor mais específico ou borda inline.
  • Checkbox/quadrado: <div> vazio com borda colapsa — use <td> com borda.
  • Linha de assinatura: evite runs longos de _; use border-top em <div>/<td> de largura fixa.
  • Renderiza bem: tabelas com border, colspan/rowspan, imagens via URL (S3), <strong>, <u>, text-rotate.

Casing: saveContrato faz mb_strtoupper em TODOS os valores postados antes do replace. O texto estático do template fica como escrito, mas todo valor sai em CAIXA ALTA. Para frase com conectivo minúsculo + dado maiúsculo, compute o placeholder no model (não monte a frase pronta na view).

 

9. Mecanismos genéricos de template (em ContratosTable.php, comuns aos 2 fluxos)

  • Bloco repetível %Pagamentos% ... %/Pagamentos% (renderBlocoRepetivel ~928): o template define o layout de UMA linha; o motor repete por item. Aditivo (só dispara se o template contém a tag). Unifica 4 fontes: select de pagamento, carnê, financiamento, veículo na troca. Tags amigáveis: %FormaPagamento%, %ValorPagamento%, %ParcelasPagamento%, %DataPagamento%... + passthrough cru (%nome_da_coluna% de cada registro).
  • Condicional %Se_Campo% ... %/Se_Campo% (~906): renderiza o miolo só se o campo top-level não-vazio.
  • Condicional por item %SeItem_Campo% ... %/SeItem_Campo% (~1631): idem, mas dentro de um bloco repetível (chave do item).
  • %Campo__ExtensoNumero% (~553): número por extenso sem "reais", p/ qualquer campo postado.
  • %ObservacoesRaw% (~438): observações via nl2br, sem rótulo e preservando o caixa.
  • Prosa editável: %DescricaoPagamento%, %DocumentacaoTransferencia% (com despachante opt-in via checkbox). Padrão "campo de prosa editável" (helper prose*() no model → textarea pré-preenchida no Gerar Contratos → motor substitui no saveContrato preservando caixa). Ao usar, adicione o campo a $preservaCaixa em ContratosItemTable.
  • %PagamentoTable% (legado, ~184 templates): montado hardcoded em vários ramos. Engessado — não mexer sem necessidade.

Modelos-PADRÃO recomendados: MeR 226 (consignação) e 227 (compra e venda) — lapidados por advogada, usam todos os mecanismos acima. Para um cliente que peça esses modelos, reuse o mesmo contrato_id (só adicione a filial à visibilidade das options + clone de cláusula opcional), em vez de criar do zero.

 

10. Cláusulas (%Clausula%)

Resolvido por getClausulaFilial(filial_id, contrato_id) (~1406): LEFT JOIN em sis_clausula_contrato por cc.user_id = filial.user_id AND cc.contrato_id. Se há registro → texto personalizado da filial; senão → fallback da coluna sis_contrato.contrato_clausula (geralmente defasado).

⚠️ Ao clonar um sis_contrato, a coluna é copiada, mas o id novo não tem linha em sis_clausula_contrato → filiais que personalizaram passam a ver o fallback. Correção: clonar os registros de cláusula do id base para o novo (derivando o user_id da filial). Cada contrato_id tem linha própria → edições são independentes (saveClausula dá UPDATE pela PK).

 

11. Dois fluxos de customização — use SEMPRE o NOVO

⚠️ Templates curinga: alguns nomes em sis_contrato_personalizado (ex: compravenda-semprop-anterior, família "sem proprietário anterior") são apontados por dezenas de filiais. Antes de editar qualquer template referenciado lá, conte quantas filiais usam (GROUP BY contrato_personalizado). Se > 1, é curinga → NÃO edite no lugar; crie um <base>-<cliente>.html e aponte só o registro do cliente.

 

12. ⚠️ Arrays hardcoded em ContratosTable.php

No topo do model há arrays de contrato_id que gateiam placeholders no geraDataContrato (fluxo da página do veículo). Se o id novo não estiver no array certo, o placeholder sai literal — mesmo com o flag contrato_procurador=1.

  • $procuracoesArray — habilita %ProcuradorData%, %Procurador%, %ClausulaProcurador_2%. Todo novo id de procuração entra aqui. ⚠️ Efeito colateral: também liga injeção de prosa no endereço do outorgante ("à RUA", "nº", "bairro", "CEP", "e RG", "residente em"). Só inclua ids cujo template descreve o outorgante em prosa corrida — se o cliente aparece em tabela com rótulos, as palavras duplicam.
  • $comprasArray — habilita %PagamentoTable% no contrato de compra (entrada). Todo novo id de compra entra aqui.
  • $consignacoesArray — análogo p/ consignação.
  • Venda NÃO usa array — é gated por contrato_venda == 1.

 

13. Procuradores (sis_filial_procurador)

Chaveado por filial_id (não por master). Dados via FilialProcuradorTable::findForFilialContract($filialId) (JOIN com sis_pessoa_cadastro). Sempre pela filial do veículo, sem fallback — filiais irmãs NÃO compartilham procuradores.

  • %Procurador% tem default = o master/loja. Só é substituído quando há procurador cadastrado (1º procurador, key 0, gated por filial_fl_procuracao == 1); os demais vão p/ %Procurador_2%.
  • "Desativar master" (filial_fl_procuracao) não zera o master sozinho — só troca quando há procurador para o lugar.
  • Diagnóstico comum: filial sem procurador em sis_filial_procurador → procurador não aparece E master "não sai". Permissão é necessária mas não suficiente; depende do cadastro naquela filial.

 

14. Pessoa Física vs Jurídica — dois cenários

  • (A) Outorgante É a própria PJ → swap automático: quando Tipo_Cliente == 2, saveContrato procura <template>-juridica.html; se existir, usa no lugar do PF. Há ~87 templates -juridica.html. Basta criá-los — o seletor já dispara o swap.
  • (B) Outorgante PF que é DONO da PJ → menção, não swap: mantém CPF/RG e acrescenta "proprietário da empresa X, CNPJ Y". Usa view custom com checkbox fl_pj + placeholder %MencaoEmpresa% resolvido no model (não na view, por causa do casing).

Campos novos postados sobrevivem ao re-render do visualizar: saveItens grava todo o POST genericamente e getItens devolve — sem precisar de coluna nova.

 

15. Passo a passo — criar um contrato novo de filial (fluxo NOVO)

  1. Achar o contrato base equivalente em sis_contrato (ex: repasse=10, garantia=4, compravenda=7, consignação=9, procuração entrada=1 / saída=8, envelope=13). ⚠️ Procuração de entrada e saída são templates diferentes — confirme o contrato_template no banco (o rótulo da option engana).
  2. Definir o próximo contrato_id — não confie só em MAX(); confira os ids referenciados nas 3 views (grep). Use o 1º id livre acima do maior referenciado.
  3. Criar o template public/template/<nome>-<cliente>.html a partir do base (respeite as limitações do mPDF).
  4. INSERT em sis_contrato copiando atributos do base.
  5. Decidir a contrato_view: manter a base, criar custom (campo novo/prefill) ou reaproveitar uma existente.
  6. Adicionar a <option> dentro do bloco da filial (if(grupo_acesso_id == 1 || filial_id_real == <FILIAL>)) em: veiculo/edit.phtml (seção compra/venda conforme entrada/saída), contratos/novo.phtml, e contratos/clausula.phtml só se tem %Clausula%. Não mexer em contratos/edit.phtml (o select ali é só exibição).
  7. Registrar o id nos arrays hardcoded de ContratosTable.php se for procuração/compra/consignação (seção 12).
  8. Clonar as cláusulas da filial (base→novo id) em sis_clausula_contrato se tem %Clausula%.
  9. Validar: php -l nas views (PHP 7.x) e gerar o PDF no navegador local você mesmo — zero %placeholder% literal, cada dado da fonte certa.
  10. Produção: o código (templates, views, arrays) vai por deploy git; os dados (sis_contrato, sis_clausula_contrato...) o usuário roda — você mostra o SQL inline no chat.

17. Regras de banco (local x produção)

  • Trabalhe no banco local (container mariadb, db boomsistemas). Produção (DBGATE_CON5_*) é réplica read-only — nunca escreva.
  • Mudanças de dados de contratos (sis_contrato, sis_contrato_personalizado, sis_contrato_configuracao, sis_clausula_contrato): NUNCA gere arquivo .sql em SQLs/. Aplique no local e mostre o SQL inline no chat — o usuário roda em produção pelo DBGate.
  • ⚠️ CRLF em cláusulas de produção: cláusulas antigas usam \r\n; um REPLACE cujo alvo cruza quebra de linha falha em prod. Prefira alvos de UMA linha ou UPDATE setando a cláusula inteira (valide por round-trip MD5).

 

18. Pegadinhas que já queimaram (lições)

  • %Valor% em contrato de compra diverge entre motores: "Gerar Contratos" posta veiculo_valor_entrada (correto); geraDataContrato usava veiculo_valor_venda no ramo de compra (corrigido via comprasArray). Sempre confira de qual campo do veículo o valor vem.
  • Lookup de pessoa por filial, não por usuário logado: o autopreenchimento divergia só para admin porque buscava pelo usuário; alinhado a getPessoaDocumentoFilial(filial_do_veículo, doc).
  • Duplicatas em sis_pessoa_cadastro: várias cópias do mesmo documento sob o mesmo master. O lookup passou a ordenar por pessoa_data_update DESC (lê a cópia editada mais recente). Risco residual no procurador (pessoa_id fixo).
  • Dessincronização local x produção: ids são hardcoded nas views; podem divergir entre ambientes. Antes de "reservar" um id, cheque as views E o banco dos dois lados.
  • O rótulo da <option> pode mentir sobre o que o id é (ex: id 218 rotulado "Procuração Compra" mas é procuração de venda da Rei-Car). Confirme o registro real + o .html.
