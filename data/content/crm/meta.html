O guard que explica a queixa original

A primeira linha útil de CrmMetaTable::receiveMessage():

if (isset($data['entry'][0]['messaging'][0]['recipient']['id']) === false
 || isset($data['entry'][0]['messaging'][0]['sender']['id'])   === false) {
    return $success;   // false — sai sem criar nada, sem log
}

É literalmente isso que a observação antiga da página descrevia. Só que ela vale para o webhook: se o evento chega sem os dois IDs, o lead nem é criado por esse caminho. O lead que o operador vê na tela nesse cenário veio do outro caminho (e-mail via Zoho), e é por isso que ele existe mas não tem chat.

Repare também que esse return é silencioso — não há handleLog aqui. Evento descartado por falta de ID não deixa rastro em lugar nenhum.

Caminho 1 — webhook nativo

Rota (segmento em module.config.php): /messengermeta-ee077033-9a15-4380-99cc-a1354ffe1132, com o comentário //uidv4 anti scan. Como na OLX, o UUID é ofuscação, não autenticação.

A filial é resolvida por $findPages, vindo de sis_filial_crm_meta_pages — a tabela que liga page_id / instagram_id → filial_id + token.

Origem: 22 ou 23, decidido pelo object

"origem_lead" => $data['object'] === 'page' ? 22 : 23,

object: "page" ⇒ Messenger (22 facebook). Qualquer outra coisa ⇒ 23 instagram. É um else aberto: um object novo da Meta cairia em "instagram" silenciosamente.

Lock de conversa — race condition real

Antes de procurar o lead, o código adquire um lock nomeado no MariaDB. O comentário documenta o incidente que originou isso:

// Lock de conversa (GET_LOCK nativo do MariaDB, mesma conexão do adapter master):
// evita que dois eventos da Meta pra mesma conversa (filial+sender+recipient), chegando
// quase simultâneos, façam o SELECT abaixo ao mesmo tempo e cada um crie o próprio lead
// (race condition confirmada — card Trello #3085, dois eventos com message_mid distintos
// no mesmo segundo). Libera sozinho se a conexão cair, sem TTL pra adivinhar.

$lockName = 'meta-lead:' . $filialId . ':' . min($senderId, $recipientId)
                                     . ':' . max($senderId, $recipientId);
$lockResult   = $this->adapter->query('SELECT GET_LOCK(?, ?) AS acquired', [$lockName, 10]);
$lockAcquired = (bool) $lockResult->current()['acquired'];
if (!$lockAcquired) {
    handleLog(false, "timeout ao adquirir lock meta-lead: {$lockName}", 'meta', 'lock-timeout', false);
}

Note o min()/max() na chave: garante o mesmo lock independente da direção da mensagem. E note que o timeout de 10s apenas loga — o código segue mesmo sem o lock, então sob contenção extrema a duplicata ainda é possível. Se aparecer lead Meta duplicado de novo, procure por pasta meta / arquivo lock-timeout no Papa Entulho.

Busca bidirecional do lead

A conversa é a mesma nas duas direções, então a busca é feita duas vezes com os IDs trocados:

// 1ª tentativa
['meta_recipient_id' => $recipientId, 'meta_sender_id' => $senderId, ...]

// 2ª tentativa — "não importa a ordem, significa ser o mesmo lead"
['meta_recipient_id' => $senderId,    'meta_sender_id' => $recipientId, ...]

Ambas filtram por status_id IN (colunas visíveis) — lead em coluna oculta não é encontrado e um novo é criado. Esse é um efeito colateral fácil de confundir com duplicação: mexer em crm_status_view muda o comportamento da integração.

Eco da própria loja

if ($senderId == $findPages[0]['instagram_id'] || $senderId == $findPages[0]['page_id']) {
    handleLog(true, "Usuário {$senderId} é o mesmo da loja, ignora criação do lead...", "meta", "own_create_lead", ...);
    return false;
}

Mensagem enviada pela loja volta como evento no webhook. Sem esse guard, toda resposta do atendente viraria um lead novo.

Nome do cliente via Graph API

A Meta não manda o nome no payload — é preciso buscar:

$fb = new \Facebook\Facebook([
    'app_id'                => getenv('facebook_crm_id'),
    'app_secret'            => getenv('facebook_crm_secret'),
    'default_graph_version' => 'v24.0',
]);
$response = $fb->get("/{$senderId}?fields=name,username", $pageAccessToken);

Ordem de fallback: name → username → "Lead Sem Nome". Falha na Graph API (permissão, usuário inexistente) é capturada e o default é mantido — o lead é criado de qualquer jeito. Um comentário registra que e-mail não é obtenível: "meta não permite". Por isso lead de Meta nasce com telefone_lead = null e email_lead ausente: o chat é o único canal de contato, o que torna a perda do meta_sender_id especialmente cara aqui.

Cada tentativa de captura de nome gera log (pasta meta, arquivo name_capture) — útil para medir quantos leads estão nascendo sem nome.

Caminho 2 — e-mail via Zoho

leadInicial() nunca inclui meta_sender_id/meta_recipient_id no array, e saveLead() só grava as colunas com a chave presente:

if (isset($lead['meta_recipient_id'])) { $data['meta_recipient_id'] = $lead['meta_recipient_id']; }
if (isset($lead['meta_sender_id']))    { $data['meta_sender_id']    = $lead['meta_sender_id']; }

Resultado: colunas NULL, chat impossível. Igual à OLX — o dado não existe no e-mail, então não há parser que resolva.

Por que "Token Meta não encontrado"

No envio (CrmIntegracaoController), o token da página é procurado em quatro tentativas, e tudo depende de meta_recipient_id estar preenchido:

$searchToken = "";
if ($lead["meta_recipient_id"]) {
    // 1. page_id      = meta_recipient_id
    // 2. page_id      = meta_sender_id
    // 3. instagram_id = meta_recipient_id
    // 4. instagram_id = meta_sender_id
}
if (empty($searchToken)) {
    return ... "msg" => "Token Meta não encontrado.";
}

As quatro variações existem porque, dependendo de quem iniciou a conversa, a página da loja pode estar em qualquer um dos dois campos — e pode ser page do Facebook ou conta do Instagram.

Diagnóstico: a mensagem "Token Meta não encontrado" tem duas causas bem diferentes:

  1. meta_recipient_id é NULL ⇒ o lead veio por e-mail. O if externo nem entra. Não tem conserto pelo lead.
  2. meta_recipient_id preenchido mas nenhuma das 4 buscas casou ⇒ a página/conta não está em sis_filial_crm_meta_pages, ou o token foi revogado. Reconectar a integração (metaCrmConnect) resolve.

Diferencie olhando a coluna antes de mandar o cliente reconectar.

Envio da mensagem

$recipientId = $lead['meta_sender_id']; // nesse caso é para quem vamos enviar a mensagem
$baseUrl = "https://graph.facebook.com/v21.0";

Com anexo, o fluxo é em duas etapas: upload do arquivo (obtém attachment_id, via stream Guzzle) e depois o envio referenciando esse id — diferente da OLX, que só manda texto.

Inconsistência a corrigir um dia: a recepção usa Graph v24.0 e o envio usa v21.0. Duas versões da API no mesmo fluxo, cravadas em arquivos diferentes — quando a Meta depreciar uma delas, só metade da integração quebra, o que torna o sintoma confuso.

Rotas de LGPD

A Meta exige endpoints de exclusão de dados para aprovar o app. Estão em module.config.php:

  • /meta/integration-delete-lgpd → metaIntegrationDeleteLGPD
  • /meta/crm-delete-lgpd → metaCrmDeleteLGPD
  • /meta/deletion-status → metaDeletionStatusLGPD (view meta-deletion-status-lgpd.phtml)

São exigência da plataforma, não feature interna — não desative essas rotas sem alinhar com quem administra o app na Meta.

Resumo para o suporte

  • Lead Meta sem chat = meta_sender_id NULL = veio por e-mail. Esperado; não é falha da filial.
  • Como Meta não fornece telefone nem e-mail, esse lead fica sem nenhum canal de contato — mais grave que na OLX.
  • Origens 53/54 são de e-mail: nunca terão chat.
  • Lead duplicado ⇒ ver meta/lock-timeout no Papa Entulho, e conferir se alguém mexeu em crm_status_view das colunas.
  • "Lead Sem Nome" ⇒ Graph API não devolveu name nem username; ver logs meta/name_capture.
