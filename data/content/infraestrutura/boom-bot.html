boom-bot

Automação que transforma cartão do Trello em Issue + branch no GitHub e depois junta as branches aprovadas numa release do gitflow. Nada chega à master sem revisão humana. Roda na estação de trabalho do dev, por comando manual, e usa o Claude Code em modo headless (claude -p) para triar e corrigir.

São duas fases, dois comandos, dois scripts:

FaseComandoScriptO que entrega
1 — produz/me_boom_bot_fixrun.pycartão do Trello vira Issue + branch bugfix/
2 — julga/me_boom_bot_releaserelease.pyrevisa as branches e monta a release/

O corte entre as duas é deliberado: a fase 1 nunca julga o próprio trabalho, e a fase 2 nunca escreve código. Nenhuma das duas escreve em master — quem roda o git flow release finish é o dev, à mão.

Hoje é ferramenta pessoal do Bruno, versionada no repo myclaude (~/.claude). Está documentada aqui porque o desenho — isolamento por worktree, permissões por etapa, trava de release e portão de aprovação humano — vale para qualquer automação de agente que a gente venha a rodar sobre os repos da Boom.

3. Fase 1 — da demanda à branch

Cada cartão dispara duas sessões headless claude -p independentes — triagem e correção —, com permissões, modelo e teto de custo próprios. Nenhuma das duas pode fazer git push ou chamar gh: quem publica é o run.py.

Cuidado com o vocabulário: fase aqui é sempre um dos dois comandos (produzir / julgar). As duas sessões headless de dentro da fase 1 são a triagem e a correção.

3.1 Contrato de saída da triagem

A triagem não devolve prosa: devolve um objeto validado pelo schema passado em --json-schema, e o envelope do --output-format json já entrega o resultado parseado no campo structured_output.

{
  "repo":      "app.boomsistemas.com.br",   // um dos 6, ou "indefinido"
  "confianca": "alta",                       // alta | media | baixa
  "titulo":    "Corrigir tela travada ao emitir NF com placa não cadastrada",
  "resumo":    "markdown, vira o corpo da Issue",
  "plano":     "markdown, vira o corpo da Issue",
  "arquivos":  ["module/Application/view/application/fiscal/upload.phtml"],
  "risco":     "texto livre"
}

repo: "indefinido" ou confianca: "baixa" encerram o fluxo na Issue. Isso é resposta desejável, não falha: abrir Issue e branch no repo errado custa mais caro que pedir decisão humana.

3.2 Correção / Fix x Investigação

O critério aceita as duas labels, e o bot sabe por qual delas o cartão entrou: o fila.py devolve o campo labels_criterio e os dois prompts recebem essa informação. A régua de sucesso muda conforme a natureza da demanda.

Na prática, cartão de Investigação tende a parar na Issue ou virar comentário com a análise, e só produz branch quando a correção aparece evidente e pequena durante a leitura do código. É de propósito: investigação que vira diff chutado é pior que investigação bem escrita.

3.3 Mapa de testes por repo

4. Fase 2 — da branch à release

O release.py é o git da fase 2. Ele não chama Claude e não escreve código: quem julga o diff é o Claude da sessão do /me_boom_bot_release, seguindo o roteiro do comando. O script faz só a parte que não pode dar errado.

release.py listar                       # branches do bot esperando release
release.py diff <repo> <branch>         # o diff contra a base, para revisar
release.py montar <repo> <br> <br> ...  # monta e empurra a release/
release.py revisar <repo> <ref>         # põe a ref de pé na 7003 (app2)
release.py status                       # releases abertas em cada repo
release.py descartar <repo> <versao>    # apaga uma release aberta

4.1 Quem é candidata

Branch origin/bugfix/AAAA.MM.DD.CARTAO com pelo menos um commit fora da base. O critério é remoto, pelo mesmo motivo do processados.json ser por máquina: branch mergeada — por PR, à mão, ou pelo merge de develop em master — passa a ter zero commits fora da base e some da lista sozinha. Não há estado local a limpar, e a lista não mente depois de um git pull feito na outra máquina.

Ficam de fora: branch escrita à mão (bugfix/especial-performance e afins, que não batem o formato do bot) e branch que já está dentro de uma release/ aberta — sem esse segundo corte, rodar o comando duas vezes no mesmo dia mandaria revisar tudo de novo.

4.2 A trava: develop em dia com a base

É a primeira coisa que o montar checa, e a razão vale o parágrafo. O git flow release finish mergeia a release em master e em develop, e a release nasce de develop — então tudo o que estiver em develop e não em master sobe junto, revisado ou não. Uma feature esquecida ali viraria produção de carona numa release de bugfix.

Com develop == base no momento da montagem, o conteúdo da release é exatamente o que foi mergeado nela, e nada mais. Se develop estiver à frente, o script recusa e imprime os commits que iriam junto; se estiver atrás, também recusa — aí o dev revisaria na tela um código diferente do que subiria. Hoje os quatro repos com develop estão 0/0 com a base, então na prática a trava não incomoda.

4.3 O que a fase 2 nunca faz

  • Checkout no clone principal. A release é montada num worktree descartável em /tmp/boom-bot-rel/, que sai no fim. O HEAD do clone do dev não se mexe — a branch local release/… fica lá porque é dela que o finish precisa depois.
  • Push em master, main ou develop. Tag. git flow release finish. O único push é o da própria release/. Fechar é do dev, com o comando que o script imprime — já com -m, porque a versão é só a data e os números dos cartões precisam ficar na mensagem da tag.
  • Release pela metade. Conflito em qualquer merge desfaz tudo: aborta o merge, apaga o worktree e a branch local, e não empurra nada. A saída é resolver o conflito na própria bugfix/ e montar de novo.

A versão é release/AAAA.MM.DD, com sufixo .2, .3 se o dia já tiver release ou tag homônima. É o formato de data das tags da equipe sem o número do cartão — porque a release justamente junta vários; os cartões ficam nas mensagens de merge e na da tag.

A conferência na tela acontece depois de montar, de propósito: uma rodada de cliques na release inteira — que é o que vai subir — em vez de uma por cartão. O preço é precisar desmontar quando um cartão cai, e para isso existe o descartar: ele apaga a release (local e no origin), as bugfix/ continuam de pé e voltam a aparecer no listar. Release que já entrou na base o script se recusa a apagar — ali o caminho é revert de commit, não delete de branch.

5. Decisões de desenho

5.1 Worktree em vez de checkout no clone principal

O bot trata um cartão por vez, sequencialmente — nunca há dois trabalhos simultâneos. Ainda assim ele não faz git checkout no clone principal, porque o conflito que importa não é bot contra bot, e sim bot contra o dev:

  • o dev está sempre numa branch própria (feature/…, hotfix/…, develop) e voltaria ao editor numa branch que não é a dele;
  • o git carrega alteração não-commitada por cima do checkout quando ela não conflita — e a correção commita o que está no working tree. Um arquivo seu aberto durante os 20-30 minutos da rodada entraria no commit do bot.

O worktree compartilha o .git do clone, então o custo é uma árvore a mais em disco, não um clone novo. Vale para os repos que ainda usam worktree — o app.boomsistemas.com.br saiu desse esquema e passou a ter um clone separado (ver 5.8); nos outros, a árvore continua em /tmp/boom-bot-wt/. Ele é criado antes da correção e removido depois — exceto quando sobra alteração sem commit dentro dele, caso em que fica de pé de propósito (ver 5.6).

5.2 Dependências por symlink

Worktree novo só materializa o que está versionado — e as dependências são gitignored na maioria dos repos. Sem tratamento, composer test e npm test quebram por falta de vendor/ ou node_modules/, produzindo um "teste falhou" que não tem relação com a correção.

RepoDependênciaVersionada?No worktree
app.boomsistemas.com.brvendor 166 MBsimvem no checkout
api.boomsistemas.com.brnode_modules 321 MBnãosymlink
boomiavendor 1,5 GBnãosymlink
boom_cronvendor 753 MBnãosymlink
boomsistemas_ci4vendor 108 MBnãosymlink

A função preparar_deps() liga cada diretório ao do clone principal. É instantâneo e não exige rede, mas tem duas consequências que estão codificadas no desenho:

  • As dependências são as da branch default. npm install, npm ci, composer install e composer update estão na denylist da correção — instalar escreveria no clone principal através do link. Correção que exija dependência nova vira impedimento no relatório, não código.
  • limpar_worktree() remove os symlinks antes do rmtree. Sem essa ordem, a limpeza seguiria o link e apagaria o vendor de verdade. Os symlinks também ficam fora da conta de "worktree sujo" (o .gitignore dos repos usa node_modules/, com barra, que não casa com symlink — sem descartá-los, todo worktree pareceria sujo para sempre).

5.3 Namespace de branch separado do gitflow

O bot usa bugfix/YYYY.MM.DD.TAREFA (constante BRANCH_PREFIX no run.py): mesmo formato de data + cartão do fluxo manual, prefixo diferente. hotfix/ é o que a equipe escreve à mão e o que o finish do gitflow transforma em tag homônima — com prefixo próprio, a branch do bot não disputa nome com a do humano no mesmo cartão e as duas se separam numa listagem (git branch --list 'bugfix/*').

A branch do bot nunca vira tag sozinha: na fase 2 ela morre dentro de uma release/AAAA.MM.DD, e a tag que sai é a da release — data, sem número de cartão. Então bugfix/ e hotfix/ do mesmo cartão no mesmo dia não disputam nome em lugar nenhum. (Antes da fase 2 existir, o caminho era o dev reaproveitar o commit à mão: foi o que aconteceu no cartão 3991, cujo commit virou hotfix/2026.08.28.3991.)

A mensagem de commit continua no padrão do repo (YYYY.MM.DD.TAREFA: descrição curta).

5.4 Por que não abre Pull Request

Abriu, até 2026-08-28. Saiu porque a PR do bot não podia ser aprovada, e PR que ninguém aprova é lixo acumulando no repo:

  • o bot usa o gh autenticado como o dev, então a PR nascia com ele de autor — e o GitHub não deixa aprovar o próprio PR: na aba Files changed sobra só "Comment", nunca "Approve";
  • e nascia em draft, que o GitHub se recusa a mergear enquanto não virar "ready for review" — dois cliques que ninguém lembrava de dar.

O que a PR entregava de útil era o diff num link, e isso o comentário na Issue entrega igual, com compare/<base>...<branch>. A Issue nasce atribuída ao dev, com a label claude-bot e sem reviewer: ninguém do time é notificado. Achar as suas: is:issue author:@me label:claude-bot.

O impedimento é de identidade, não de configuração — enquanto o autor for a conta do dev, não existe Approve. A saída, se um dia fizer falta, é o bot deixar de ser o dev no GitHub: uma machine account na org com PAT próprio, e aí o Approve humano volta a valer. Enquanto isso não existir, reabrir PR seria voltar ao mesmo lixo — quem faz o papel de revisão hoje é a fase 2.

5.5 Idempotência

Cartão em "Em andamento" fica dias na lista, então rodar duas vezes não pode gerar duas Issues. São três camadas, da mais barata para a mais confiável:

  1. ~/.local/state/boom-bot/processados.json — estado local, por máquina;
  2. git ls-remote --heads origin 'refs/heads/*.<n>' nos 6 repos — busca por sufixo, então reconhece a branch mesmo que ela tenha nascido em outro dia (ou com o prefixo do fluxo manual) e pega trabalho já publicado de qualquer máquina;
  3. busca de Issue com trello #<n> no título — best-effort, a indexação do GitHub tem atraso.

Um flock em ~/.local/state/boom-bot/lock garante uma rodada por vez na mesma máquina.

5.6 O hook rtk come a allowlist da correção

Precedente real, cartão 3982 em 2026-08-28. A fase de correção escreveu o fix inteiro (dois arquivos, CrmTable.php e um .phtml), acumulou 19 permissões negadas, terminou sem commit — e o limpar_worktree() apagou o worktree com o diff dentro. Sobrou uma Issue com relatório em prosa descrevendo um código que não existia em lugar nenhum: nem em branch, nem em disco. A recuperação só foi possível porque os Edit ficam gravados no transcript da sessão (~/.claude/projects/<slug-do-cwd>/<session-id>.jsonl), com old_string e new_string — dá para reaplicar de lá.

A causa não estava no bot. O ~/.claude/settings.json da estação tem um hook PreToolUse — rtk hook claude, um proxy de compactação de saída instalado por fora — que reescreve todo comando Bash antes de ele ser avaliado. Confira em qualquer máquina:

rtk hook check "git commit -m x"     # => rtk git commit -m x
rtk hook check "grep -rn foo ."      # => rtk grep -rn foo .

A forma reescrita (rtk git commit …) não casa com nenhuma regra Bash(git commit:*) do settings-fix.json, então cai em pedido de aprovação; e em sessão headless não existe quem aprove. O efeito é duplo e traiçoeiro: a allowlist deixa de valer (o modelo perde comandos que deveria ter) e a denylist deixa de proteger (o deny de git push não casa com rtk git push). Pior: como o modelo viu git status, git log e git diff negados, concluiu que "git está bloqueado" e desistiu do commit — que estava liberado.

Duas defesas. A primeira já está no código:

  • Worktree com alteração sem commit não é apagado. limpar_worktree() devolve False, escreve o caminho no log e o diff vai para /tmp/boom-bot-wt/<repo>--<n>.diff, fora do worktree — sobrevive a qualquer limpeza posterior. A função é salvar_diff_pendente(), e ela usa git add -N (intent-to-add) para arquivo novo aparecer no patch.
  • A rodada seguinte respeita o worktree preservado em vez de recriá-lo: para no cartão e diz o motivo.
  • Guarda de branch em uso: se o clone principal estiver justamente na branch que o bot ia criar, ele para no cartão com mensagem clara em vez de estourar um erro cru de git.

A segunda é a lista de permissões, que precisa das duas formas de cada comando — a nua e a com rtk :

"allow": [ "Bash(rtk git add:*)", "Bash(rtk git commit:*)", "Bash(rtk git status:*)",
           "Bash(rtk git diff:*)", "Bash(rtk git log:*)", "Bash(rtk grep:*)",
           "Bash(rtk rg:*)", "Bash(rtk ls:*)", "Bash(rtk wc:*)", "Bash(rtk find:*)",
           "Bash(rtk php -l:*)", "Bash(rtk npm test:*)", "Bash(rtk composer test:*)" ],
"deny":  [ "Bash(rtk git push:*)", "Bash(rtk git checkout:*)", "Bash(rtk git reset:*)",
           "Bash(rtk git branch:*)", "Bash(rtk git worktree:*)", "Bash(rtk gh:*)",
           "Bash(rtk mysql:*)", "Bash(rtk docker:*)", "Bash(rtk aws:*)",
           "Bash(rtk curl:*)", "Bash(rtk npm install:*)", "Bash(rtk composer install:*)",
           "Bash(rtk run:*)", "Bash(rtk proxy:*)", "Bash(rtk pipe:*)" ]

Os três últimos do deny não são opcionais: rtk run, rtk proxy e rtk pipe executam comando cru via sh -c. Sem eles na lista, todo o resto dos negados é contornável por uma linha.

Alternativa mais limpa, ainda não testada: rodar as sessões do bot com o hook desligado (variável RTK_DISABLED) em vez de manter a lista duplicada. Enquanto isso não for feito, vale reler a linha de permissões negadas do log depois de cada rodada — é ela que denuncia o problema.

5.7 Toda Issue termina com a resposta pronta para o suporte

O relatório da fase de correção é escrito para dev — cita arquivo, linha, nome de método. Só que quem abriu a demanda foi o suporte, e alguém precisa responder o cartão do Trello em português de gente quando a correção subir. Fazer essa tradução à mão, depois, é o tipo de passo que se esquece.

Por isso o prompt-fix.md obriga o relatório a fechar com uma seção ## Resposta para o suporte: 3 a 5 linhas em bloco de citação, sem jargão — nada de arquivo, classe, tabela, SQL, código de rejeição, branch ou número de PR. Diz o que mudou na prática e o que a pessoa precisa fazer (ou que não precisa fazer nada), no passado, sem prometer data de deploy.

O run.py recorta essa seção com resposta_para_suporte() e a publica como comentário separado na Issue, com a ressalva "depois que a branch for revisada e subir". Fica a um ctrl+C de distância, sem caçar no meio do relatório — e a Issue passa a ter, no fim, exatamente o texto que vai para o cliente.

Se o modelo esquecer a seção, o log registra relatório veio sem a seção "Resposta para o suporte" e nada é inventado: melhor faltar do que o suporte colar no cartão um texto que ninguém escreveu de propósito.

5.8 O ambiente 2 — o clone app2 na porta 7003

Todo relatório do bot terminava com "não validado na tela", e não é desleixo: o app não tem suíte que rode sem ambiente de pé, então o que ele entrega é diff mais análise, sem prova visual. A saída foi um segundo ambiente completo: Projects/app2.boomsistemas.com.br, um clone independente do repo — .git, .env, vendor e node_modules próprios — servido na porta 7003 pelo mesmo nginx do stack.

7002.worktrees/currentlegado do boom-wt, se ainda for usado

Não é worktree. São dois repositórios: dois .git, dois checkouts desprendidos, dois terminais ao mesmo tempo sem stash nem troca de branch. O que os dois compartilham é só o banco local, e é de propósito — cópia de 7,4 GB envelheceria rápido, e o auth.setup.js do E2E resolve o usuário consultando justamente esse banco. O custo é disco (≈470 MB), que sobra.

Do lado do run.py:

  • CLONES mapeia repo → pasta do clone + URL. Para quem está no mapa o bot não cria worktree: preparar_clone() faz fetch + checkout -B ali mesmo. Os outros repos seguem em worktree descartável no /tmp.
  • Recusa quando há alteração rastreada sem commit, e salva o diff em Projects/app2.boomsistemas.com.br.diff. A pasta é compartilhada com o uso manual do dev; passar por cima do trabalho dele é exatamente o que não pode acontecer. Arquivo não rastreado não bloqueia — o checkout não mexe nele — e só entra no log.
  • docker exec php7 kill -USR2 1 depois da troca: o php-fpm cacheia realpath por 120 s e sem isso a branch nova leva até 2 min para aparecer no navegador.
  • A branch fica de pé depois da rodada (não há limpeza no clone): é assim que se revisa o cartão na tela, abrindo a 7003.

O ambiente 2 serve as duas fases. A fase 1 trabalha o cartão ali (é o preparar_clone() acima); a fase 2 sobe ali a release/ já montada, com release.py revisar, que faz o mesmo checkout -B mais o kill -USR2 do php-fpm. Em ambos os casos o app2 recusa a troca se houver alteração rastreada sem commit — a pasta é compartilhada com o uso manual do dev, e passar por cima do trabalho dele é o que não pode acontecer. Para o repo do app, todo trabalho do bot e toda conferência na tela acontecem na 7003; a 7000 é só do dev.

Em máquina nova, além do docker compose up -d nginx php7: criar a pasta (clone do GitHub, ou cp -a do principal), copiar o .env com o BASE_URL apontando para http://localhost:7003, e acrescentar as duas entradas de safe.directory no git global (o caminho no host e o /var/www/…) — o container php7 faz chown -R www-data no /var/www e o git recusa repositório de outro dono.

Como cada .env é uma cópia, eles envelhecem: variável nova entra num ambiente e o outro segue sem ela, o que aparece como bug de tela em vez de config velha. O comando /me_boom_env_sync compara os dois (e as worktrees, se houver) e classifica — faltando, valor diferente, só existe num lado — sem nunca imprimir valor de variável.

Duas coisas que ainda não estão fechadas: a fase de correção não abre o navegador sozinha (precisaria de Bash(npx playwright…) na allowlist dela e de um caminho de login em dev), e o .env do clone é o do ambiente real do dev, com os segredos de verdade, num diretório onde a sessão headless roda — se isso incomodar, o lugar de fechar é "deny": ["Read(./.env)"] no settings-fix.json.

7. Como rodar

Pelo comando global, de qualquer diretório:

/me_boom_bot_fix                 # fase 1, rodada normal: Issue + branch
/me_boom_bot_fix --dry-run       # lista a fila e as checagens, sem chamar Claude nem GitHub
/me_boom_bot_fix --so-triagem    # só a triagem, imprime o JSON, não toca no GitHub
/me_boom_bot_fix --card 1605     # força um cartão pelo nº da tarefa
/me_boom_bot_fix --force         # reprocessa mesmo já existindo Issue ou branch

/me_boom_bot_release             # fase 2: revisa as branches e monta a release
/me_boom_bot_release --repo boomia   # só um repo

Digitar /me_boom_bot no menu filtra e mostra as duas fases.

Direto, sem passar por uma sessão do Claude:

python3 ~/.claude/scripts/boom-bot/run.py --dry-run
python3 ~/.claude/scripts/boom-bot/fila.py --human              # só ver a fila
python3 ~/.claude/scripts/boom-bot/fila.py --human --sem-label  # ignorar o filtro de label

python3 ~/.claude/scripts/boom-bot/release.py listar            # o que espera release
python3 ~/.claude/scripts/boom-bot/release.py status            # releases abertas

Na primeira vez num repo, vale a escada: --so-triagem para conferir se ele acerta o repo, depois --card N para ir até o fim num cartão só, e só então a rodada sem argumento.

Voltar ao automático é uma linha de crontab, mas aí releia a seção de idempotência — habilite numa máquina só:

0 * * * * /usr/bin/python3 $HOME/.claude/scripts/boom-bot/run.py >> $HOME/.local/state/boom-bot/cron.log 2>&1

7.1 Rodar sem parar o seu trabalho

O lugar de rodar em paralelo é o Terminator, não uma sessão do Claude: /me_boom_bot_fix prende a sessão que você usou pelos 20-30 min de cada cartão. O comando avisa e pergunta antes de disparar — mas não barra, porque deixar rodando e sair para o almoço é caso de uso legítimo. Rodando por fora, o próprio run.py percebe (env CLAUDECODE), deixa o aviso no log e segue.

Menu de botão-direito do Terminator:

EntradaO que faz
BOOM-BOTa rodada normal
BOOM-BOT (dry-run)só lista a fila e as checagens de duplicidade
BOOM-BOT (log)tail -f no log do dia

O ~/.config/terminator/config é por máquina e não viaja no myclaude — quem viaja é o instalador. Uma vez por PC, depois do /me_sync:

python3 ~/.claude/scripts/boom-bot/instala-terminator.py            # idempotente
python3 ~/.claude/scripts/boom-bot/instala-terminator.py --dry-run  # só mostra

Ele faz backup do config, insere as entradas no plugin CustomCommandsMenu com a próxima position livre e corrige o comando se a entrada já existir com valor diferente. O Terminator só lê o config ao abrir: feche e abra a janela.

Dá para disparar a rodada e continuar na sua branch de feature: no clone principal o bot só executa git fetch origin <default> e git worktree add/remove/prune. Nenhum desses mexe no seu HEAD, no índice, nos arquivos abertos ou nos stashes — o checkout do bot acontece na árvore de /tmp.

SituaçãoO que acontece
Você está em feature/x e roda o botnada muda no seu diretório; ele trabalha em /tmp/boom-bot-wt/
Você está na branch que o bot vai criarele para naquele cartão e loga o motivo (o git não deixa duas árvores usarem a mesma branch)
Você roda git no exato instante do worktree adddisputa de index.lock; é raro e o comando pede para repetir
Sobra um worktree preservado de rodada anterioro cartão seguinte daquele número para e avisa, até você resolver o /tmp

Uma tarefa por vez, sempre. O bot nunca roda dois cartões em paralelo: ele fecha um inteiro — triagem, Issue, worktree, correção, comentário — antes de olhar o próximo. O BOT_MAX_CARDS não tem relação com paralelismo; é freio de custo por rodada, e em 0 a rodada simplesmente varre a fila até o fim. A última linha do log soma o custo equivalente de todas as sessões da rodada.

Onde você trabalha em paralelo: no app2, o mesmo clone que o bot usa (ver 5.8). São dois repositórios de verdade, servidos em portas diferentes — dois terminais, dois checkouts, sem stash e sem troca de branch. O combinado é simples: se você deixar alteração rastreada sem commit lá, o bot para no cartão em vez de passar por cima; commite ou guarde antes de mandar uma rodada.

8. Limites conhecidos

  • Branch protection é a trava real. A allowlist de ferramentas do Claude é trava local e tem furos conhecidos de casamento por prefixo (git -C <path> push não casa com o deny de git push, e um hook que reescreve o comando fura os dois lados da lista — ver 5.6). O que garante que nada entre na master/main sem revisão é a branch protection no GitHub — vale ligar nos 6 repos.
  • Custo. Uma triagem em sonnet num cartão real de suporte ficou em ~US$ 1,00 e ~6 minutos rodando em xhigh — o effortLevel herdado do ~/.claude/settings.json. Por isso o bot passa --effort explícito: sessão headless herda a config global do dev, e triagem no topo da escala é desperdício. Os freios de custo são BOT_EFFORT_*, BOT_BUDGET_* (corta a sessão ao atingir o teto) e BOT_MAX_CARDS — este último hoje em 0 (sem teto), então o freio efetivo por cartão é o budget. A rodada fecha o log com o total equivalente gasto.
  • Assinatura x API. Com login claude.ai, o total_cost_usd do log é o preço equivalente na API, não uma cobrança: o consumo real sai do limite de uso do plano. O número serve para comparar rodadas, não para prever fatura.
  • Dado pessoal. Cartão de suporte traz CPF, telefone, endereço e placa, inclusive nos prints. Os dois prompts proíbem copiar isso para Issue ou commit — o filial_id do título pode aparecer, por ser id interno. Quem escreve o texto é o modelo: confira na revisão.
  • Produção nunca é tocada. Acesso a banco, migrations e chamadas externas de escrita estão na denylist das duas etapas da fase 1. A fase 2 não roda código nenhum: só git.
  • Duas máquinas. O estado local é por máquina; a proteção contra duplicar é remota. Rodando manual, basta. No cron simultâneo em duas máquinas existe janela de duplicação.
  • gh 2.4.0 (pacote Ubuntu, de 2022) não tem gh label — o run.py cria a label pela API REST. Atualizar o gh não quebra nada.
  • A fase 2 não roda testes de novo. A revisão é leitura do diff (com os chamadores em volta) mais a conferência na 7003; os testes são os que a fase 1 já rodou, e o que ela conseguiu rodar está na seção Testes da Issue. Em repo sem suíte (app, socket) o peso todo fica na tela.
  • A release é por repo. Uma rodada da fase 1 pode espalhar cartões por vários repos; cada um vira a sua própria release/, com o seu próprio finish. E repo sem develop (hoje o socket) não tem release do gitflow: ali o caminho continua sendo hotfix/ por cartão.

9. Depurar

tail -f ~/.local/state/boom-bot/logs/$(date +%F).log
cat ~/.local/state/boom-bot/logs/1605-triagem.json   # envelope cru do claude -p
cat ~/.local/state/boom-bot/processados.json
ls  /tmp/boom-bot-wt/                                # worktree preservado + .diff pendente
ls  /tmp/boom-bot-rel/                               # worktree de montagem da release

As duas fases escrevem no mesmo log do dia. A fase 2 registra montando release/…, cada merge … e … empurrada; quando ela recusa, a mensagem vai para o stderr do comando e não para o log — é o texto que explica o motivo, e vale colar inteiro em vez de resumir. Estado da fase 2 é sempre remoto: release.py listar e release.py status respondem consultando o origin, então não há arquivo de estado para ficar mentindo.

Três linhas do log valem procura direta: worktree PRESERVADO (sobrou diff sem commit — o caminho vem na sequência), diff pendente salvo em (onde está o patch) e parando na Issue (o cartão foi abandonado antes do código, com o motivo).

O log registra, por fase: custo em dólar, duração, número de turnos e as permissões negadas. Essa última linha é o primeiro lugar para olhar quando o bot rende pouco — comando negado por formato (por exemplo cd X && git log, que só passa se cd também estiver na allowlist) faz o modelo gastar turnos contornando em vez de investigar.
